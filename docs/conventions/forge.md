# Forge and git

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## Git authentication and errors (CLAUDE-252)

Every `git` subprocess authenticates from the forge key store and reports why it failed (CLAUDE-252). `provider::shallow_clone` is the one clone path for all three actions, and `provider::git_error` builds every git failure as the exit code PLUS the tail of git's own stderr, redacted through `forge_log::redact` with the URL's userinfo passed as a known secret (the reason string reaches `run_events` and can reach a YouTrack comment, and the clone URL carries a token). Before it, `git clone exited 128` and `git push exited 1` were the entire diagnosis for a missing credential, an unknown host, a deleted branch, a rejected non-fast-forward and a protected branch alike. The `youtrack` action was also the only one cloning the UNauthenticated URL from the YouTrack VCS integration ("host git identity handles auth"), which is exactly what a container does not have, so every job failed at the pre step; it now resolves through `Forge::clone_url` like the other two, stripping the scheme from `repo_host` because that lookup wants a bare host, and falls back to the plain URL with a `warn`, so a configured git credential helper still applies. `{{clone_url}}` in the prompt stays unauthenticated: the agent must never be handed the token.

`shallow_clone` also checks out every submodule, when the repo has any (CLAUDE-376): after a successful clone (and, for a pinned branch, after `restore_default_branch_refs`), `init_submodules` runs `git submodule update --init --recursive --depth 1` whenever the workdir has a `.gitmodules` file, and is a silent no-op otherwise. A repo that vendors its task runner as a submodule (`storefront`'s `justfile` importing `common`) used to clone with an empty submodule directory, so the agent's first `just pre-commit` failed. A relative submodule URL resolves against the superproject's own remote, so it inherits the same token-bearing clone URL `Forge::clone_url` already produced; no separate credential lookup is needed. A submodule fetch failure goes through the same `git_error` path as every other git failure here (redacted stderr, no silent fallback) rather than a warning followed by a half-populated tree.

The token never lives in the job workdir, and never reaches a child process's argv, either (CLAUDE-395). Once a clone (and its submodules, recursively) succeed, `shallow_clone` scrubs `origin`'s URL and every `submodule.<name>.url` and submodule `remote.origin.url` back to userinfo-free, so a workdir left on disk, in a PR diff, or copied into a bug report carries no credential. A rewrite failure (e.g. `.git/config` locked) fails the clone through the same `git_error` path as every other git failure here, rather than leaving a token-bearing remote behind silently. Every git network call the runner issues afterwards (`cli.rs`'s `ls-remote`/`fetch`/`push`, `github.rs`'s `push`, and `workdir.rs`'s `local_only_work` preserve-or-delete `ls-remote`) re-authenticates per invocation instead: `provider::run_authed_git` / `provider::authed_git_output` resolve the token from the forge's own key store at call time, then pass it to git only via `-c credential.helper=` (clearing any inherited helper) followed by an inline `-c credential.helper=!sh -c '...'` that echoes the username/password from two environment variables set on that one child process. The token is in argv nowhere and in `.git/config` never; `url.<authed>.insteadOf=` was considered and rejected for exactly that reason, since it persists into the repo's own config. A call site with no token to resolve (no `github.token_ref`, no forge key configured, the GC sweep's context-free preserve check) falls back to running the same command unauthenticated against `origin`, with the existing `warn`, so a host relying on its own ambient git credentials keeps working unchanged.

## Read-only fj retries (CLAUDE-366)

Every read-only `fj` call the runner makes is retried up to four attempts total on a transient failure (CLAUDE-366), because a `Forge` read (`repo view`, `pr search`, `pr status`, `whoami`, `repo collaborator ... permission`, and the CI-failure `FjForgeReads` log/run/file reads) is idempotent and a bare `fj` exit failure is often a momentary forge blip rather than a real denial. `CliBackend` and `FjForgeReads` each carry their own `fj_read_retry_waits: [Duration; 3]` field (default `[0s, 2s, 5s]`, overridable in tests via `with_fj_read_retry_waits`), and every read call site routes through the shared `run_fj_read_retrying` helper in `src/provider/cli.rs`: it retries only on `Ok(out)` with `!out.ok` (a non-zero exit), never classifies by parsing `stderr` wording, and lets a spawn failure (`Error::CliNotFound`) through unretried since the binary itself is missing. A failed non-final attempt logs at `warn` naming the command, the attempt number, and the stderr tail; a recovery after a failed attempt logs at `info`; a call that fails all four attempts returns the last attempt's `Error::CliFailed` unchanged, so a deterministic failure (a 404, a scope error) still surfaces its real cause after paying the worst-case 7 seconds of added delay. Every `fj` write (`pr create`, `pr merge`, `pr update`, PR/issue comments, label edits) is excluded on purpose: retrying a write risks a duplicate comment or PR, with one deliberate exception on the git side, not the `fj` side: see "Git network retries" below for why a git `push` retries safely where an `fj` write does not. The wait itself runs through `crate::blocking::in_place` (CLAUDE-228), never a bare `std::thread::sleep`, so a retried read on a failing forge does not stall a tokio worker thread.

## Git network retries (CLAUDE-396)

Every git network call the runner makes is retried up to four attempts total on a transient failure (CLAUDE-396), the same shape as the read-only `fj` retry above: a shared `retry_git_network` helper in `src/provider/mod.rs`, a `GIT_NETWORK_RETRY_WAITS: [Duration; 3] = [0s, 2s, 5s]` constant, retry only on a completed process with a non-zero exit (never a spawn error, never by classifying `stderr` wording), waits through `crate::blocking::in_place`, a `warn` log per failed non-final attempt (git op, attempt number, redacted stderr tail) and an `info` log on recovery. It covers all eleven runner-owned git network call sites: `shallow_clone`, `init_submodules` and `restore_default_branch_refs`'s `ls-remote`/`fetch` in `src/provider/mod.rs`; `remote_branch_sha`, `fetch_branch` and `push_branch` in `src/provider/cli.rs`; both branches of `GithubForge::push` in `src/provider/github.rs`; `workdir.rs`'s preserve-or-delete `ls-remote`; and the comment webhook's `git_push` in `src/web/comment_webhooks.rs`. A clone retry starts from an absent target directory: a failed first attempt can leave `workdir` half-populated, and `git clone` refuses to clone into a non-empty directory, so the retry removes whatever is there first.

`push` is the one WRITE that retries here, unlike every `fj` write above: pushing a fixed commit to a fixed ref name is idempotent, so a retry that lands after an earlier attempt already succeeded server-side exits 0 with "Everything up-to-date" rather than duplicating anything, and a genuine rejection (non-fast-forward, protected branch, missing scope) still surfaces unchanged once the four attempts are exhausted. No site ever gains `--force` or a force-equivalent refspec to make that idempotency hold. The AGit `fj pr create -aA` path (`src/provider/cli.rs`) is excluded from both retries: it pushes AND opens a PR in one `fj` write, so retrying it could open a duplicate PR, and it stays under the CLAUDE-366 fj-write exclusion rather than this one.
