# Forge and git

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## Git authentication and errors (CLAUDE-252)

Every `git` subprocess authenticates from the forge key store and reports why it failed (CLAUDE-252). `provider::shallow_clone` is the one clone path for all three actions, and `provider::git_error` builds every git failure as the exit code PLUS the tail of git's own stderr, redacted through `forge_log::redact` with the URL's userinfo passed as a known secret (the reason string reaches `run_events` and can reach a YouTrack comment, and the clone URL carries a token). Before it, `git clone exited 128` and `git push exited 1` were the entire diagnosis for a missing credential, an unknown host, a deleted branch, a rejected non-fast-forward and a protected branch alike. The `youtrack` action was also the only one cloning the UNauthenticated URL from the YouTrack VCS integration ("host git identity handles auth"), which is exactly what a container does not have, so every job failed at the pre step; it now resolves through `Forge::clone_url` like the other two, stripping the scheme from `repo_host` because that lookup wants a bare host, and falls back to the plain URL with a `warn`, so a configured git credential helper still applies. `{{clone_url}}` in the prompt stays unauthenticated: the agent must never be handed the token.

`shallow_clone` also checks out every submodule, when the repo has any (CLAUDE-376): after a successful clone (and, for a pinned branch, after `restore_default_branch_refs`), `init_submodules` runs `git submodule update --init --recursive --depth 1` whenever the workdir has a `.gitmodules` file, and is a silent no-op otherwise. A repo that vendors its task runner as a submodule (`storefront`'s `justfile` importing `common`) used to clone with an empty submodule directory, so the agent's first `just pre-commit` failed. A relative submodule URL resolves against the superproject's own remote, so it inherits the same token-bearing clone URL `Forge::clone_url` already produced; no separate credential lookup is needed. A submodule fetch failure goes through the same `git_error` path as every other git failure here (redacted stderr, no silent fallback) rather than a warning followed by a half-populated tree.

The token never lives in the job workdir, never reaches a child process's argv, and never sits in `.git/config` at any point in a git process's lifetime, either (CLAUDE-395, CLAUDE-410). Every runner-owned git invocation that takes a URL - `provider::shallow_clone`'s clone, the pinned-branch `ls-remote`/`fetch` in `restore_default_branch_refs`, `init_submodules`'s `submodule update`, `cli.rs`'s `ls-remote`/`fetch`/`push`, `github.rs`'s `push`, `workdir.rs`'s `local_only_work` preserve-or-delete `ls-remote`, and the comment webhook's `git_push` - authenticates per invocation through `provider::authed_git_command` / `provider::run_authed_git`: these resolve the token from the forge's own key store at call time, then pass it to git only via `-c credential.helper=` (clearing any inherited helper) followed by an inline `-c credential.helper=!f() { echo "username=$CLAUDE_RUN_GIT_USERNAME"; echo "password=$CLAUDE_RUN_GIT_PASSWORD"; }; f` that echoes the username/password from two environment variables set on that one child process. The git argument itself is always the userinfo-free URL (`provider::strip_userinfo`), never the token-bearing one; the token travels only through the two environment variables. Because the clone records a plain `origin`, the follow-on `fetch` and `submodule update` calls carry the same helper args and environment so they still authenticate; a `-c` option and its environment both propagate to the submodule processes git itself spawns, so a same-host relative submodule URL authenticates the same way with no separate credential lookup. `shallow_clone` still scrubs `origin`'s URL and every `submodule.<name>.url` and submodule `remote.origin.url` back to userinfo-free afterwards, as a verification step and a backstop if a future call site regresses, not because the clone leaves a credential behind to clean up. A rewrite failure there (e.g. `.git/config` locked) fails the clone through the same `git_error` path as every other git failure here, rather than leaving a token-bearing remote behind silently. The token is in argv nowhere and in `.git/config` never; `url.<authed>.insteadOf=` was considered and rejected for exactly that reason, since it persists into the repo's own config. A call site with no token to resolve (no `github.token_ref`, no forge key configured, the GC sweep's context-free preserve check) falls back to running the same command unauthenticated against `origin`, with the existing `warn`, so a host relying on its own ambient git credentials keeps working unchanged. The `-c` pair and the two credential variables ARE inherited by anything that git invocation spawns for the duration of the call: git re-exports every `-c` as `GIT_CONFIG_PARAMETERS` to a hook it runs, so the runner's own `git push` leaves a repo's `pre-push` hook holding both the config parameters and `CLAUDE_RUN_GIT_USERNAME` / `CLAUDE_RUN_GIT_PASSWORD` in its environment (CLAUDE-426). A hook that runs the test suite must therefore not assume a clean ambient git environment; `testutil::clear_ambient_git_env` strips that fixed set of variables before a test execs real git.

The agent's own `git` authenticates to the configured Forgejo host through a credential helper, not a token (CLAUDE-411). `materialize` writes `[credential "https://<forgejo_host>"]` into the file `GIT_CONFIG_GLOBAL` names, with an empty `helper =` (clearing any inherited helper list for that host) followed by `helper = !fj auth git-credential`, so the agent's plain `git clone`, `fetch`, `ls-remote` and submodule calls against that host answer from the same `keys.json` `fj` reads. The stanza is scoped to the one host, so the token is never offered to any other HTTPS host the agent contacts, and it is rewritten on the next materialize when the host changes in Settings -> Auth. The token is still never handed to the agent as a string: not in `{{clone_url}}`, its environment, its argv, or any repo or git config file. The helper adds no capability the agent lacks, since it already runs as the owner of `/data` and can read `keys.json` itself. It needs a `fj` that ships `auth git-credential` (FJ-114); the image build's smoke check runs `fj auth git-credential --help` so a base without it fails the build. The runner's own per-invocation helper above is unchanged.

A failed CLI call reports the tail of its stdout as well as its stderr (CLAUDE-422). A `pre-push` hook (`just pre-push`, which runs `cargo test`) writes its test report to the hook's stdout, and git does not fold hook stdout into its own stderr, so a stderr-only message named no failing test. `provider::append_stdout_tail` appends the last 40 lines (at most 4000 bytes) of stdout under a `--- stdout ---` marker after the stderr text, redacted through `forge_log::redact` with the call's known secrets before it is cut, and returns stderr unchanged when stdout is empty. `provider::git_error` and `CliBackend::checked` (every `fj`, `yt` and `git` failure in `cli.rs`) both apply it; the git network call sites pass the token URL's secrets. The retry log's `stderr_tail` is unchanged. The timeout-salvage `git add` / `git commit` in `src/native/youtrack.rs`'s `commit_timeout_wip` applies the same `append_stdout_tail` rule to its own failure text (CLAUDE-432), since `git commit` there runs the repo's `pre-commit` hook and a failing hook's report lands on stdout, not stderr.

## Read-only fj retries (CLAUDE-366)

Every read-only `fj` call the runner makes is retried up to four attempts total on a transient failure (CLAUDE-366), because a `Forge` read (`repo view`, `pr search`, `pr status`, `whoami`, `repo collaborator ... permission`, and the CI-failure `FjForgeReads` log/run/file reads) is idempotent and a bare `fj` exit failure is often a momentary forge blip rather than a real denial. `CliBackend` and `FjForgeReads` each carry their own `fj_read_retry_waits: [Duration; 3]` field (default `[0s, 2s, 5s]`, overridable in tests via `with_fj_read_retry_waits`), and every read call site routes through the shared `run_read_retrying` helper in `src/provider/cli.rs` (generalized from `run_fj_read_retrying` by CLAUDE-407 to serve `gh` too; see the GitHub paragraph below): it retries only on `Ok(out)` with `!out.ok` (a non-zero exit), never classifies by parsing `stderr` wording, and lets a spawn failure (`Error::CliNotFound`) through unretried since the binary itself is missing. A failed non-final attempt logs at `warn` naming the command, the attempt number, and the stderr tail; a recovery after a failed attempt logs at `info`; a call that fails all four attempts returns the last attempt's `Error::CliFailed` unchanged, so a deterministic failure (a 404, a scope error) still surfaces its real cause after paying the worst-case 7 seconds of added delay. Every `fj` write (`pr create`, `pr merge`, `pr update`, PR/issue comments, label edits) is excluded on purpose: retrying a write risks a duplicate comment or PR, with one deliberate exception on the git side, not the `fj` side: see "Git network retries" below for why a git `push` retries safely where an `fj` write does not. The wait itself runs through `crate::blocking::in_place` (CLAUDE-228), never a bare `std::thread::sleep`, so a retried read on a failing forge does not stall a tokio worker thread.

The GitHub backend gets the same treatment for its `gh` reads (CLAUDE-407): `GithubForge::identity`, both `repo_access` probes (`repo view`, `pr list`), `list_open_prs`, `repo_permission`, the `gh pr view ... isDraft` read inside `refresh_pr_text`, and `pr_status` each carry their own `gh_read_retry_waits: [Duration; 3]` field (default `[0s, 2s, 5s]`, overridable via `with_gh_read_retry_waits` on `GithubForge`), and route through a private `run_gh_read` that calls the same shared `run_read_retrying` helper and schedule (`DEFAULT_READ_RETRY_WAITS` in `src/provider/cli.rs`) as the `fj` reads above, with identical logging. `GhForgeReads::api_get`, the single entry point behind its `find_run` / `run_logs` / `list_runs` / `run_timing` / `read_file` reads, carries its own `gh_read_retry_waits` field the same way. Excluded on purpose, exactly like the `fj` writes above: `gh pr create` (PR open), `gh pr comment` / `gh issue comment`, `gh pr ready`, the `gh pr edit` half of `refresh_pr_text`, `merge_pr`, and `update_pr_branch` (CLAUDE-405) each fail on their first and only attempt, since retrying any of them risks a duplicate PR, comment, merge, or branch update. `gh auth token` and `gh --version` are local-only (no network request) and are not retried either.

## Git network retries (CLAUDE-396)

Every git network call the runner makes is retried up to four attempts total on a transient failure (CLAUDE-396), the same shape as the read-only `fj` retry above: a shared `retry_git_network` helper in `src/provider/mod.rs`, a `GIT_NETWORK_RETRY_WAITS: [Duration; 3] = [0s, 2s, 5s]` constant, retry only on a completed process with a non-zero exit (never a spawn error, never by classifying `stderr` wording), waits through `crate::blocking::in_place`, a `warn` log per failed non-final attempt (git op, attempt number, redacted stderr tail) and an `info` log on recovery. It covers all eleven runner-owned git network call sites: `shallow_clone`, `init_submodules` and `restore_default_branch_refs`'s `ls-remote`/`fetch` in `src/provider/mod.rs`; `remote_branch_sha`, `fetch_branch` and `push_branch` in `src/provider/cli.rs`; both branches of `GithubForge::push` in `src/provider/github.rs`; `workdir.rs`'s preserve-or-delete `ls-remote`; and the comment webhook's `git_push` in `src/web/comment_webhooks.rs`. A clone retry starts from an absent target directory: a failed first attempt can leave `workdir` half-populated, and `git clone` refuses to clone into a non-empty directory, so the retry removes whatever is there first.

`push` is the one WRITE that retries here, unlike every `fj` write above: pushing a fixed commit to a fixed ref name is idempotent, so a retry that lands after an earlier attempt already succeeded server-side exits 0 with "Everything up-to-date" rather than duplicating anything, and a genuine rejection (non-fast-forward, protected branch, missing scope) still surfaces unchanged once the four attempts are exhausted. No site ever gains `--force` or a force-equivalent refspec to make that idempotency hold. The AGit `fj pr create -aA` path (`src/provider/cli.rs`) is excluded from both retries: it pushes AND opens a PR in one `fj` write, so retrying it could open a duplicate PR, and it stays under the CLAUDE-366 fj-write exclusion rather than this one.

## Divergence fetch uses a real tracking ref (CLAUDE-464)

The runner's workdir is always a `--single-branch` shallow clone (`shallow_clone` in `src/provider/mod.rs`), so its configured `remote.origin.fetch` refspec covers only the branch the clone was pinned to at creation time; a bare `git fetch origin <branch>` naming any OTHER branch (the agent's own feature branch, created locally off a default-branch-pinned clone per `CLAUDE.md` step 3) writes `FETCH_HEAD` only and creates no `refs/remotes/origin/<branch>`. `CliBackend::create_pr_branch`'s divergence leg calls `merge_remote_branch`, which runs `git merge --no-edit origin/<branch>`, and that lookup fails with "not something we can merge" unless the tracking ref exists. `fetch_branch` therefore names the destination explicitly: `git fetch origin refs/heads/<branch>:refs/remotes/origin/<branch>`, with no leading `+`, since the ref never exists yet in a fresh workdir and a rejected update on a later call would be a real signal rather than something to force past. Every other `git fetch origin <ref>` call site followed by a read of `origin/<ref>` already uses an explicit `+refs/heads/<ref>:refs/remotes/origin/<ref>` destination (`restore_default_branch_refs` in `src/provider/mod.rs`) or reads only `origin/HEAD`/`origin/<default-branch>`, which the clone's own pinned refspec or `restore_default_branch_refs` already tracks, so this was the one violation.

## Open-PR lookup degradation (CLAUDE-206, CLAUDE-469)

Both backends adopt an already-open PR for the branch instead of failing a create on it. `CliBackend::find_or_create_pr` (`src/provider/cli.rs`) looks the PR up with `fj pr search` before calling `fj pr create`; `GithubForge::create_pr_impl` (`src/provider/github.rs`) does the same with `gh pr list` (also for the MCP path) before `gh pr create` or the MCP `create_pull_request` tool (CLAUDE-469 ported the Forgejo behavior here, so this is not Forgejo-only). On either backend a failed lookup degrades to "assume no open PR" rather than discarding the run, logging a `warn` and recording an operator-visible notice; a create then rejected because a PR for that head already exists retries the lookup exactly once and adopts the result, or names both the lookup and create causes if that also fails. See [Open-PR lookup degradation](../../actions/SCHEMA.md#open-pr-lookup-degradation-claude-206-claude-469) in `actions/SCHEMA.md` for the full behavior.

## Push comments on every PR-branch write (CLAUDE-447)

Every runner-owned write to a PR branch posts exactly one PR comment afterward, through the shared `push_comment` module (`src/push_comment.rs`), so the PR's own timeline explains how the branch reached its current state instead of leaving that only in YouTrack or a log. `PushEvent` names six kinds: `initial push (PR opened)`, `resumed-run push`, `timeout salvage push`, `comment-webhook fix push`, `merged remote branch before push`, and `branch updated from base` (a seventh, `CheckpointPush`, is reserved for CLAUDE-448 and not wired to any call site yet). `push_comment::build_body` renders the event label, the issue key, the PR's draft/ready state, the old/new SHA range, and the commit subjects (newest first, capped at `MAX_COMMIT_LINES` = 20 with `... and N more` beyond that, or `(commit subjects unavailable: ...)` for a server-side forge operation with no local clone to run `git log` against), then appends the CLAUDE-446 run footer.

The five call sites: `CliBackend::create_pr_branch`'s three legs and `create_pr_agit` (`src/provider/cli.rs`, covering `initial push`, `resumed-run push`, `merged remote branch before push`, and, via `create_pr_with_draft`'s `draft` override, `timeout salvage push`); `GithubForge::create_pr_impl` (`src/provider/github.rs`, the same three applicable kinds, GitHub having no AGit equivalent and no adopt-on-diverged path); the comment-webhook fix push (`push_fix`/`git_push` in `src/web/comment_webhooks.rs`, which reads the issue key back out of the pushed tip's commit body via `provider::bare_issue_key`, CLAUDE-398, since `VerifiedCommentCommand` carries no YouTrack key field); and `update_pr_branch` for the automerge behind-base path (`src/web/webhooks.rs`), which is the one event with no local clone at all, so its `CommitSubjects` is always `Unavailable`, its new SHA always `unknown`, and its draft state always `false` (automerge only acts on a ready PR).

`push_comment::post` writes the body to a scratch file named `claude-run-push-comment-<pr_number>-<event_label_with_spaces_and_parens_as_underscores>.md` (the caller's git-directory scratch when a local clone exists, a temp directory otherwise), calls `Forge::pr_comment`, and removes the file afterward. A failed post is a write (CLAUDE-366/CLAUDE-407) and is therefore never retried: `post` logs it at `error` and returns `Some("PR comment for <event> failed: <cause>")` for the caller to fold into its own outcome surface, and `None` on success; either way the push or branch update it reports on is already done and is never undone, failed, or rolled back because the comment failed. Each caller folds that `Option<String>` into whatever outcome surface it already owns rather than posting a second, separate failure comment: the YouTrack `finalize()` success and timeout-salvage paths (`src/native/youtrack.rs`) append it to the success comment or the timeout comment respectively, the comment-webhook reply (`outcome_comment` in `src/web/comment_webhooks.rs`) appends a `Note:` line, and the automerge outcome string (`src/web/webhooks.rs`) appends it in parentheses.
