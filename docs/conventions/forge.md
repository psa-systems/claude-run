# Forge and git

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## Git authentication and errors (CLAUDE-252)

Every `git` subprocess authenticates from the forge key store and reports why it failed (CLAUDE-252). `provider::shallow_clone` is the one clone path for all three actions, and `provider::git_error` builds every git failure as the exit code PLUS the tail of git's own stderr, redacted through `forge_log::redact` with the URL's userinfo passed as a known secret (the reason string reaches `run_events` and can reach a YouTrack comment, and the clone URL carries a token). Before it, `git clone exited 128` and `git push exited 1` were the entire diagnosis for a missing credential, an unknown host, a deleted branch, a rejected non-fast-forward and a protected branch alike. The `youtrack` action was also the only one cloning the UNauthenticated URL from the YouTrack VCS integration ("host git identity handles auth"), which is exactly what a container does not have, so every job failed at the pre step; it now resolves through `Forge::clone_url` like the other two, stripping the scheme from `repo_host` because that lookup wants a bare host, and falls back to the plain URL with a `warn` so a host install using a credential helper is unchanged. `{{clone_url}}` in the prompt stays unauthenticated: the agent must never be handed the token.

## Read-only fj retries (CLAUDE-366)

Every read-only `fj` call the runner makes is retried up to four attempts total on a transient failure (CLAUDE-366), because a `Forge` read (`repo view`, `pr search`, `pr status`, `whoami`, `repo collaborator ... permission`, and the CI-failure `FjForgeReads` log/run/file reads) is idempotent and a bare `fj` exit failure is often a momentary forge blip rather than a real denial. `CliBackend` and `FjForgeReads` each carry their own `fj_read_retry_waits: [Duration; 3]` field (default `[0s, 2s, 5s]`, overridable in tests via `with_fj_read_retry_waits`), and every read call site routes through the shared `run_fj_read_retrying` helper in `src/provider/cli.rs`: it retries only on `Ok(out)` with `!out.ok` (a non-zero exit), never classifies by parsing `stderr` wording, and lets a spawn failure (`Error::CliNotFound`) through unretried since the binary itself is missing. A failed non-final attempt logs at `warn` naming the command, the attempt number, and the stderr tail; a recovery after a failed attempt logs at `info`; a call that fails all four attempts returns the last attempt's `Error::CliFailed` unchanged, so a deterministic failure (a 404, a scope error) still surfaces its real cause after paying the worst-case 7 seconds of added delay. Every `fj` write (`pr create`, `pr merge`, `pr update`, PR/issue comments, label edits) is excluded on purpose: retrying a write risks a duplicate comment or PR. The wait itself runs through `crate::blocking::in_place` (CLAUDE-228), never a bare `std::thread::sleep`, so a retried read on a failing forge does not stall a tokio worker thread.
