# Log and state retention

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## Stream-log sweep (CLAUDE-245)

`logs/` is bounded by its own sweep (CLAUDE-245). Nothing deleted stream logs before it: `crate::gc::sweep` walks `workdirs/*/*` and `crate::retention::sweep` prunes DB tables, and neither looked at `logs/`, so the directory only ever grew (2473 files / 2.8 GB on host-a, oldest five months back). That is the root cause of CLAUDE-233 rather than a separate bug: the full log partition is what made the relay's write fail. `crate::gc::sweep_stream_logs` is the second sweep in the same module, deleting `logs/<action>/streams/*.jsonl` past `config.stream_log_gc.retention_days` (default 30) and logging its deleted / kept / bytes-reclaimed tally every pass at `info`. `daemon::stream_log_gc_loop` schedules it beside the other two on the `GC_TICK_SECS` cadence, first tick at serve start, reading the live handle so a Settings save applies next pass. What keeps an in-flight run's log is `daemon::inflight_stream_log_jobs`: the `(action, job_key)` pairs from `run_inflight_jobs` joined to runs with `ended_at IS NULL`, kept regardless of age, because a long `claude_timeout_seconds` job can outlive any window while its log is still being written. A failed read of that set skips the pass rather than sweeping with an empty set, since the wrong guess deletes a live run's only transcript.

## Workdir `target/` sweep (SPEC-3.10 item 5, CLAUDE-511)

A preserved or aside workdir (`<key>.kept-<n>`) can hold local-only work for weeks before `crate::gc::sweep` reaches it on age alone, and the preserve / set-aside decisions only looked at git state, so a Rust repo's multi-GB `target/` rode along for the whole `retention_days` / `unpushed_hard_cap_days` window. `crate::workdir::cleanup_or_preserve_with_token`, the one guarded delete every caller shares (the native YouTrack action, scripted-action jobs in `src/job.rs`, the comment webhook in `src/web/comment_webhooks.rs`), now calls `crate::gc::remove_target` before either branch that keeps `workdir` returns, so no caller of the shared preserve decision can keep a `target/` inside it; `crate::native::youtrack`'s separate `preserve_aside` set-aside path calls the same helper before it moves a leftover workdir out of the way. `crate::gc::sweep` calls the same helper on every workdir older than one day, independently of the kept/deleted decision that follows it unchanged, so a workdir already being kept for local-only work (or simply under the retention window) still loses `target/` once it is a day old. The removal covers a `target/` a build left behind despite `CARGO_TARGET_DIR` pointing at the shared per-repo cache (`SPEC-3.10` items 2-3), for example a project that sets its own `build.target-dir`. Each removal is logged at `info` with the key, path and bytes reclaimed (rolled into the pass's `bytes_reclaimed` tally); a failed removal is logged at `error` with the OS error, counted in `SweepStats.target_removal_failed`, and never read as success.

## Size-bounded log files (CLAUDE-257, CLAUDE-268)

The other three writers under `logs/` are bounded by SIZE on that same tick (CLAUDE-257, CLAUDE-268). `logs/daemon.log` (opened `create+append` by `detach_now` and handed to daemonize as both stdout and stderr) and `logs/<action>/<output.file>` (`job::append_output_record`, opt-in per action) are single files appended to for the life of the install, so an age window never fires on either: `crate::gc::sweep_oversized_logs` copies a file past its ceiling to one predecessor (`<name>.1`, skipped by the walk so it is never rotated again) and truncates the original IN PLACE back to its newest half at a line boundary. In place because the daemon holds `daemon.log` open in append mode; a rename would leave it writing into the predecessor while the live log stayed empty. `logs/usage.jsonl` (DEV-707's per-run token and cost record, `usage::append_record`) is the third: it sits directly under `logs/`, so the action-directory walk never reaches it and it is bounded explicitly beside `daemon.log`, and because it is newline-delimited JSON the existing line-boundary cut is what keeps the survivor parseable instead of starting mid-record (CLAUDE-268). The ceilings extend `config.stream_log_gc` (`daemon_log_max_bytes` / `output_file_max_bytes`, 50 MiB each, `usage_log_max_bytes`, 8 MiB because a usage record is far shorter than a log line, `0` = unbounded) rather than adding a fourth loop, and the settings key keeps its `stream_log_gc` name because renaming the document's primary key would silently reset an operator's configured window. The `output.file` sink is bounded by size and never age-swept on purpose: it is an operator-configured data sink, and deleting it destroys the record it exists to keep. The `$CLAUDE_RUN_STATE_DIR` tree in `actions/SCHEMA.md` had described the removed nu runner (a `PAUSED` file, `state/<name>.json`, a dated `.log`) until CLAUDE-257 replaced it with the paths that exist.

## Snippet and webhook-log sweeps (CLAUDE-262)

The last two trees under the state dir are bounded the same way, by AGE, on the same tick (CLAUDE-262). `snippets/<action>/<job_key>/` (`crate::snippet::snippet_dir_for`) is written once per scripted step (`filter` / `pre` / `prompt` / `post`) of every job and nothing ever removed it; `crate::gc::sweep_snippets` deletes a directory past `config.stream_log_gc.snippet_retention_days`, reusing the exact `run_inflight_jobs`-derived in-flight set `sweep_stream_logs` reads so a still-running job's own snippet directory is never deleted underneath it, and a failed in-flight read skips both sweeps for the same reason it skips the stream-log one. `webhook-logs/` (`crate::forge_log::write_artifact`, one redacted concatenated log per triaged CI run) is bounded the same way by `crate::gc::sweep_webhook_logs` against `config.stream_log_gc.webhook_log_retention_days`, but age-only with no in-flight guard: a webhook run is not a scheduled job and never appears in `run_inflight_jobs`. That sweep walks only the FILES directly under `webhook-logs/`, never its subdirectories, because `webhook-logs/analysis/<owner>_<repo>-run<N>/` (CLAUDE-274, replacing the old shared `webhook-logs/triage/`) is a PER-EVENT working directory the at-ingest `AnalysisClassifier` creates and removes itself once its session returns, not a per-run artifact the GC sweep needs to bound. Both new windows ride the existing `config.stream_log_gc` document rather than a fifth section, per the same "the settings key is the document's primary key" reasoning CLAUDE-257 used to keep that section's name unchanged.

## Docker sidecar volume sweep (CLAUDE-433)

Agent sessions drive a privileged Docker-in-Docker sidecar (`DOCKER_HOST`), and the dev stacks they start create named volumes (cargo registry, cargo git, build target, Postgres data) that nothing removed: one deployment held 139 named volumes totalling about 206 GB, 138 of them referenced by no container, and the sidecar's data directory filled to 100%. `crate::gc::sweep_docker_volumes` removes a named volume once it is older than `config.docker_gc.volume_retention_days` (default 3) AND no container currently references it, reusing the EXACT `SweepStats` tally shape (deleted / kept / bytes-reclaimed, logged at `info` every pass) the other sweeps in this module use. `daemon::docker_gc_loop` schedules it on the same `GC_TICK_SECS` cadence, first tick at serve start, reading the live handle so a Settings save applies next pass. Docker records no last-used time, so age means time since creation: a volume a session reused minutes ago is still removed once it crosses the window, and the cost is a rebuild or re-seed. A `buildx_buildkit_*` state volume is kept at any age. The sweep talks to the Docker daemon through an injected `DockerVolumeClient` trait (`list_volumes` / `remove_volume`), so the age / in-use / buildx-prefix decision logic is unit-testable without a real Docker daemon; `crate::gc::CliDockerVolumeClient` is the production implementation, shelling out to the `docker` CLI against whatever `DOCKER_HOST` already points it at (the same sidecar agent sessions use), the same way `src/test_postgres.rs` already shells out to `docker` for the throwaway test-Postgres container. It never passes `--force` on a remove or `--all` on a list/prune, since `--all` has no age filter; Docker's own refusal of an in-use volume (a race between the list and the remove) is logged at `info` and left in place, and any other remove failure is logged at `error` naming the volume. When `DOCKER_HOST` is unset or the daemon is unreachable, the pass is SKIPPED and logged at `warn` naming the cause, never reported as a clean sweep.

## Docker storage ceiling reclaim (SPEC-3.11, CLAUDE-516)

The volume sweep above only ever removes unreferenced named volumes, so a sidecar can still fill its data directory through stopped containers, dangling and unused images, and build cache, none of which that sweep touches. `crate::gc::reclaim_docker_storage` measures the sidecar's total Docker storage (`DockerVolumeClient::usage`, summing images / containers / local volumes / build cache the same way `docker system df` reports them) against the new `config.docker_gc.max_bytes` ceiling (default 250 GB, validated `>= 1` the same way `volume_retention_days` already is) and, only once the total exceeds it, reclaims in a fixed order until back under the ceiling or out of categories: stopped containers older than one day, then dangling images, then build cache older than seven days, then unused images older than seven days, then (reusing `sweep_docker_volumes` itself as the last step) unreferenced volumes past the existing window. Each step logs its category, bytes reclaimed, and the before/after total at `info`, and the pass stops as soon as the running total drops back under the ceiling rather than running every category regardless. Nothing a running container references is ever removed: `reclaim_images` checks each image's computed `in_use` flag (derived from `docker inspect --format '{{.Image}}'` across live containers) before considering it, the same in-use guard the volume sweep already applies to volumes. Build cache is the one documented exception to the "never pass a force flag" rule in this file: `docker builder prune` has no by-id removal, so `reclaim_build_cache` calls it with `--force --filter until=168h` and nothing else, never `--all`. `daemon::docker_gc_loop` runs this pass on the same `GC_TICK_SECS` cadence as the volume sweep, but first asks `api::activity` whether any run is in flight; a run in flight skips the whole pass and logs that it did, since a run may be using the sidecar itself, and a failed in-flight read is treated as "in flight" (fail closed) rather than risking a reclaim mid-run. A failed `usage()` read is logged at `error` and reclaims nothing that pass, never reported as clean.

## Per-repo Cargo target cache ceiling (SPEC-3.10 item 6, CLAUDE-512)

Each repo's shared `cargo-target/<repo-slug>/` directory (`SPEC-3.10` items 2-3) is itself unbounded: nothing before CLAUDE-512 ever shrank it, so a repo's directory only grows across every run that builds it. `crate::gc::sweep_cargo_cache` walks the immediate subdirectories of `paths.cargo_cache_dir()` and deletes any directory over `config.cargo_cache.max_bytes_per_repo` (default 60 GB, validated `>= 1`) once no run for that repo is in flight, logging the delete at `warn` with the repo, size, and ceiling; the next run for that repo rebuilds cold. A directory's size is read with an error-propagating walk (`crate::gc::dir_size_checked`, unlike the best-effort `dir_size` the workdir sweep uses), so an unreadable entry skips that directory and logs at `error` instead of silently reading as "zero bytes, under ceiling". There is no DB column recording which repo a job is building, so in-flight evidence is derived rather than queried directly: `daemon::cargo_cache_gc_loop` reads the same `run_inflight_jobs`-joined `(action, job_key)` pairs the stream-log sweep already uses, then `daemon::inflight_cargo_repos` resolves each pair's workdir to its git remote (`git -C <workdir> remote get-url origin`, blocking, run off the tokio worker) and that URL to its `repo_slug`. A pair whose workdir has no readable remote yet (not cloned, or a transient git failure) simply does not contribute evidence for that one job rather than failing the whole pass; a failed `run_inflight_jobs` read, or a failed resolution task, is treated as "evidence unavailable" for the tick, in which case every over-ceiling directory is kept and logged at `error` rather than risked deleted blind. `daemon::cargo_cache_gc_loop` runs on the same `GC_TICK_SECS` cadence as the other sweeps, reading the live `config.cargo_cache` handle so a Settings save applies on the next pass.
