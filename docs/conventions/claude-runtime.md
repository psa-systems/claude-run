# Claude invocation and runtime

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## No blocking on tokio workers (CLAUDE-228)

No blocking work runs on a tokio worker thread (CLAUDE-228). `src/blocking.rs` `in_place` wraps every synchronous subprocess and sleep reached from an async context: the `yt` / `fj` / `git` exec in `provider::cli::ProcessRunner`, `ClaudeInvoker::invoke`'s spawn-and-wait, the `nu` exec in `src/snippet.rs`, and each runner's sync `run_pre` / `finalize` / gather / cleanup call. It is `block_in_place` behind a `RuntimeFlavor::MultiThread` check (that call panics on the `current_thread` runtime `#[tokio::test]` builds), chosen over `spawn_blocking` because it takes a bare `FnOnce` and the call sites keep their borrows. Left inline, one 3600s `claude` session pinned one worker for its whole duration, tasks holding sqlx pool connections went unpolled, and the daemon logged `pool timed out while waiting for an open connection` while no single statement was slow. Two supporting pieces landed with it: `concurrency::GatherGate`, a per-action marker so the scheduler skips a pickup whose previous gather is still running (overlapping RUNS stay deliberate per CLAUDE-162; overlapping GATHERS were never intended), and `state::RunGuard`, which closes a `run_begin` row on every exit path including an early `?`, so a transient error can no longer strand a row that the web UI renders as a running job. The DB-level sweeps are the backstop a long-lived daemon never reaches: `state::reap_orphaned_runs` at serve start closes every row still open as `exit::UNEXPECTED` (nothing cancelled it; the count logs at `warn`), and `state::cancel_orphaned_runs` at shutdown closes what the stop actually cancelled as `exit::CANCELLED`. `state.rs` also carries the mechanical pairing test that fails if a runner ever calls `run_begin` without a `RunGuard`. `src/db.rs` states the pool's `max_connections` (16), `acquire_timeout` (30s) and `acquire_slow_threshold` (5s) explicitly rather than inheriting sqlx's defaults.

## Per-run spend budget (DEV-705, DEV-707)

Spend is bounded per RUN and accounted per run (DEV-705 / DEV-707), in `src/usage.rs`. The invariant: every run resolves a spend ceiling from configuration BEFORE it starts, bills every `claude` invocation against one shared ledger, checks the ledger before every job pickup, and terminates with `exit::OVER_BUDGET` (6) and a reason naming the budget rather than asking for the budget to be raised. `limits.run_budget_usd` (unset = the action's effective `daily_budget_usd`) is snapshotted into `EffectiveLimits`, which is `Copy` and moved into each per-job task by value, so the ceiling is structurally un-raisable mid-run; `limits.budget_warn_fraction` (default 0.80) fires one `warn` on the way there. Between pickups a single session could still overshoot, so `ClaudeInvoker::invoke` takes the run's remaining dollars and passes them as `--max-budget-usd`. The ledger is `usage::RunSpend`, created once per run in `daemon::run_action_inner` and carried to native handlers on `NativeContext::spend`; `run_action_inner` now returns the run's exit code so a standalone `claude-run run` exits non-zero on an over-budget stop. Accounting comes from replaying each invocation's stream log (`usage::parse_stream_usage`): tokens by category per turn, tool call counts, and per-tool attribution (a turn is attributed to the tool whose result most recently entered its context). Each run emits one `run usage` line and appends one NDJSON record to `logs/usage.jsonl`. Cost of record is the CLI's own `total_cost_usd`, never a hard-coded price table, so a price change needs no runner release.

## Plan rate-limit readings (CLAUDE-315)

Every `claude` invocation records its own Claude plan (subscription) rate-limit reading, separate from the dollar spend above (CLAUDE-315). `usage::parse_stream_usage` also replays a stream log's `rate_limit_event` (a `status` plus a `five_hour` / `seven_day` window utilization, kept as the LAST one seen so a session's own retries do not average out) and every `api_retry` event (counted per reason into a `BTreeMap`); every field stays an `Option` and is never defaulted to `0` or `"unknown"`, because an old CLI or a session that made no API call reporting one leaves genuinely no data rather than a zero. `ClaudeInvoker::invoke` logs one `claude usage` line per invocation, at `warn` instead of `info` when the status is not `allowed` or either window's utilization is at least 0.9, and states `rate_limit = "absent"` explicitly when there was no event at all. `usage::record_invocation` then persists one row to the `claude_invocations` table (`migrations/{sqlite,postgres}/00{22,3}_claude_invocations.sql`) at every call site that invokes `claude` in `src/` (`job.rs`, `native/youtrack.rs`, `triage.rs`, `web/comment_webhooks.rs`), immediately after `invoke` returns and before any branch can drop the result; a write failure logs at `error` and never fails the job, because the invocation itself already succeeded or failed on its own terms. `src/state.rs`'s `every_claude_invoke_call_site_pairs_with_a_record_invocation_call` is a source-scan test (modeled on the CLAUDE-228 run-guard pairing test) that fails if a new `.invoke(` call site is added with no matching `record_invocation(` call beside it. The table joins `RETENTION_TABLES` (per-occurrence history, not a lookup table) and `import::TABLES` / `IDENTITY_COLUMNS` (so switching backends carries it over). `/reports` renders it as the "Claude plan usage" section: `report::claude_usage` queries the window, `web::build_usage_chart` turns it into an inline-SVG two-series line chart (five-hour and seven-day utilization, 0-100%) that breaks into a new polyline segment at each invocation with no rate-limit data at all rather than interpolating a fabricated reading, and flags a timed-out or failed invocation's marker in red; the section states the gap count explicitly and shows an empty-state message when the window holds no invocations, plus a table of the 20 most recent.

## Bounded context (DEV-706)

Context is bounded per invocation, which is what makes spend linear in tool calls (DEV-706). `claude.autocompact` resolves action -> `config.claude.autocompact` -> `claude::DEFAULT_AUTOCOMPACT` (200000), and unlike `model` / `effort` the last step is a VALUE rather than no flag: the CLI's own `auto` scales the window to the model's whole context, so on a 1M-context model a long tool-heavy session never compacts, resends every completed operation's tool payloads on every turn, and cumulative spend grows with the SQUARE of the number of tool calls with tool output rather than reasoning dominating the bill. `StreamUsage::context_per_tool_call` (in the per-run record) is the measurement: flat as N grows is linear, rising with N is quadratic. `usage.rs`'s `context_per_tool_call_separates_quadratic_growth_from_linear` pins both shapes.

## Stream-log write failures (CLAUDE-233)

The stream-log relay reports its own I/O failures instead of truncating in silence (CLAUDE-233). `relay_stamped_stdout` (`src/claude.rs`) is the only writer of `logs/<action>/streams/<key>-attempt-<n>.jsonl`, and it used to `break` on a write error with the error discarded. When the log partition filled, it stopped mid-line, claude kept running and exited 0, `parse_final_result` found no `result`, and the run was failed non-transiently as "claude stream did not end with a result event" - blaming the agent for a silence the runner produced, and burning an attempt against `max_attempts_per_key`. The relay now returns `io::Result`, `invoke` carries the reason out of the wait block, and a relay that died before the terminal `result` yields a `transient` failure naming the write error and the log path (`relay_failure_result`), so no attempt is spent; when the `result` was already captured the run still finalizes from it and the truncation logs at `warn`. The forensic signature of the old bug in an existing log is a file ending mid-line at an exact multiple of 4096, the page boundary where the kernel's short write stopped.

## Stream-log read failures (CLAUDE-256)

The READ side of that same file carries its `io::Error` out too, instead of collapsing it (CLAUDE-256). `parse_final_result` and `last_assistant_text` (`src/claude.rs`) both return `io::Result` rather than swallowing a read failure into `None` or an empty string. A stream log the runner cannot read finalizes as `read_failure_result`, `transient`, so it spends no attempt and is picked up again on the next poll; a log that reads fine but simply never got a `result` event keeps its existing non-transient "claude stream did not end with a result event" wording, because that is a real claude-side outcome rather than a runner fault.

CLAUDE-382: `friendly_failure_summary`'s last-resort fallback, for a log with no terminal `result` event and no assistant text, is no longer a byte-sliced tail of the raw stream (a per-event-type dump of bare `assistant`/`user`/`system`/`tool_use=` lines that read as noise, and that used to need a UTF-8-boundary-aware cut point, CLAUDE-263). It now states plainly that the run produced no final message, names the number of assistant turns recorded and the last tool used (if any), and points at the stream log path for the full detail.

## No background work (CLAUDE-280)

No `claude` child can leave work running past its own turn (CLAUDE-280). `ClaudeInvoker::invoke` (`src/claude.rs`) sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` in every child's environment and passes `--disallowedTools=Monitor,ScheduleWakeup` unconditionally, for every caller (the native runners, the triage classifier, the comment webhook, and scripted jobs): a session run under `--print` is over the instant its turn ends, so a turn that ends "waiting" for a `Bash` background task, a `Monitor`, or a `ScheduleWakeup` never resumes, and run 10822 (CLAUDE-269) is what happened without this - a session that reported success while `cargo test --lib` was still running in the background. `wait_or_cancel` already terminates a leftover background task that outlives the terminal `result`, and that termination is the backstop this issue adds: `killed_tasks_after_result` (`src/claude.rs`) scans the stream log for a `system`/`task_updated` event with `patch.status: killed` AFTER the terminal `result`, and a match overrides what would otherwise be a captured success into a non-transient failure naming the task id. `parse_final_result` still selects the `result` event by type rather than by line position (CLAUDE-107), so a clean run with ordinary trailing `system` events is unaffected; only a *killed* one flips the outcome.
