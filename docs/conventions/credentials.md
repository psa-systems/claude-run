# Credentials and logins

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## Readiness gate (CLAUDE-269)

Nothing runs without a Claude credential (`src/readiness.rs`). The scheduler tick, `Dispatcher::execute` and the trigger endpoint all consult `ReadinessGate` the way they consult `pause::PauseGate`, and the two states stay distinct: a pause is an operator decision, unready is an instance that was never finished. Ready means any of a `.credentials.json` in the agent config dir, a stored API key, or `ANTHROPIC_API_KEY` in the env. The transition is logged once in each direction rather than per tick; the dashboard shows a banner and `/api/status` carries `ready` + `not_ready_reason`. This is what stopped a fresh container from querying YouTrack every tick and logging an auth error per action, on runs that could only have failed at the `claude` call and burned an attempt. CLAUDE-269 adds a second, independent not-ready axis on the same gate: `login_required`, an expired or revoked login the credential check alone cannot see because `.credentials.json` stays on disk. `ReadinessGate::trip_login_required` / `clear_login_required` are called from `ClaudeInvoker::invoke` (a structured `authentication_failed` on the stream, or three repeated `system`/`api_retry` events well before `claude_timeout_seconds`) and from a daemon status probe (`claude auth status --json`, `src/service_auth.rs::probe_claude_login`, run at startup, every 10 minutes while ready, every 60 seconds while login-required, skipped on `no_credential`); detection matches only the structured `error` field, never the CLI's human-readable wording. `pause::PauseGate::with_readiness` carries the gate into every `RunPause`, so the existing per-job checkpoints stop a run for this reason too, with no new call sites, closing with `exit::LOGIN_REQUIRED` (8) rather than `exit::PAUSED`. It clears with no restart on a completed brokered sign-in, an API-key save, or the probe reporting `loggedIn: true`.

## Brokered Claude login

`claude auth login` is brokered from the Settings Auth card (`src/claude_login.rs`), so the container gets a real subscription login and not just an API key. The CLI's redirect is a paste-the-code callback, not a `localhost` listener, and over pipes it prints the authorize URL then reads the code from stdin: the broker spawns it under the agent config dir, hands the URL to the page, and writes the pasted code back. The child is held in daemon state between the two requests because it owns the PKCE verifier; a refused code returns the CLI's own wording and keeps the session (the CLI re-arms its prompt), cancel and a 15-minute expiry kill it, and the spawn plus the bounded read run through `blocking::in_place` per CLAUDE-228.

## Service logins and secrets key (CLAUDE-307)

The daemon holds its own service logins, entered in the web UI (Settings -> Auth, the card at the top of `/settings`). `src/service_auth.rs` materializes them where the CLIs actually look: a single-file `yt` config at `<config_dir>/auth/youtrack.yml` named by `YOUTRACK_CLI_CONFIG` (exported once at serve start, before any child, so a later save needs no restart and a per-job `token_ref` still wins by setting the same var in the child's own env), a `keys.json` in the daemon's XDG data dir through the same `secrets::write_fj_keys` the per-job path uses, a GitHub `hosts.yml` written by `gh auth login --with-token` itself under `<config_dir>/auth/gh` named by `GH_CONFIG_DIR` (CLAUDE-307; every `gh` child, including `GithubForge`'s own lazy `gh auth token --hostname <host>` fallback used when an action sets no `github.token_ref`, then reads that same login with no restart), and an `ANTHROPIC_API_KEY` handed to `ClaudeInvoker` through an `Arc<RwLock<Option<String>>>` the Settings save swaps. The `config.auth` document (section `Auth`) stores only URLs, the Forgejo host, the GitHub host, and the four fixed secret names; the tokens live encrypted in the secrets store. That store needs no pre-provisioned key and the runner owns it: `secrets::ensure_key` (serve start, and the CLI before it writes) puts it at `<config_dir>/secrets.key`, 0600. Config, not data, because the ciphertext is `state.db` in the data dir and a key beside its ciphertext defeats the point of encrypting the store; a key still at the old `<data_dir>/secrets.key` is MOVED on the next start. Generation happens only while the store is empty: a missing key with secrets already stored is a hard error naming them, never a silent replacement that would orphan them. `SecretsKey::load` is now a plain read with one behaviour. The key is extracted from wherever it sits on a line, so a SOPS-decrypted `data: AGE-SECRET-KEY-...` or an env-style file works as a key file, and a group- or world-readable key file loads with a `warn` rather than failing (an operator's delivery may be 0644 deliberately). This is what fixes the container's `no instance configured. Run 'yt auth login'` on every poll: the daemon's own provider calls had nothing but host auth, and a container has no host operator.
