# Throwaway test Postgres (CLAUDE-404)

`claude-run test-postgres [--image <ref>] [--init-sql <file>]... [--network <name>] -- <command> [args...]` is how an agent session (or anyone else) runs a Postgres-backed test command: it starts a private, non-durable Postgres container in the Docker-in-Docker sidecar every agent session already has, runs `<command>` against it, and tears the container down however the command ends. CLAUDE-403 stopped the `claude` child from reaching the runner's own live database, which otherwise left Postgres-backed suites (claude-run's own `CLAUDE_RUN_TEST_DATABASE_URL` pass, and other repos' suites that read `DATABASE_URL`) unverified until CI; this subcommand is the replacement.

## What it does

1. Sweeps orphaned containers first: any earlier `claude-run-test-postgres-*` container labelled `claude-run.test-postgres=<pid>` whose owning pid is no longer alive is stopped, since containers started by hand are not reliably removed.
2. Starts `docker run --detach --rm` with a loopback-only ephemeral publish (`--publish 127.0.0.1::5432`, the port read back with `docker port`), or, with the optional `--network <name>`, on that Docker network with nothing published, reached by container name on port 5432; plus `--shm-size 256m`, `--memory 4g`, a raised `max_connections` as a server flag after the image name (`-c max_connections=200`: the parallel fixture leg builds many small pools at once and the default 100 is too few, CLAUDE-540), and a random per-run password. The default image is `docker.io/postgres:18.4-alpine3.23`; `--image` overrides it so a repo whose CI pins a different tag (app-server uses `postgres:18.2-alpine3.23`) can match it. No tmpfs, no volume: the container's own writable layer is discarded by `--rm`, and the data directory is never put on the host's RAM-backed tmpfs (a large suite, about 1,300 cloned databases in app-server, can fill it).
3. Waits for a `psql` connection to succeed (up to 60s), over the same unix socket path every later step connects through, rather than `pg_isready`: the official postgres image's entrypoint restarts the server once after its own `initdb`, and `pg_isready` can report ready during the brief window before that restart, which is no guarantee that `psql`'s own connection succeeds. Then disables durability (`fsync`, `synchronous_commit`, `full_page_writes` all `off`, reloaded with `pg_reload_conf()`, verified by reading `SHOW fsync` back) since a throwaway database does not need to survive a crash: app-server measured this cutting a 229-migration run from 1.12-1.32s to 0.60-0.71s. Both the settings change and the `SHOW fsync` read-back retry for up to 20s against a connection failure that looks like that restart (the "starting up" / "shutting down" messages, or the unix socket going missing mid-restart), logging the first such retry at `warn`; a failure that does not look like a restart, or one still failing once the window elapses, fails the run immediately. With `--network`, it also opens a TCP connection to the URL it will hand the command, from its own process, for up to 20s before applying `--init-sql`: `psql` answering inside the container says nothing about whether the command can reach it, and a caller that runs in a container of its own cannot reach the Docker host's loopback, so this check fails within seconds and names `--network` instead of letting every test time out on its pool (CLAUDE-541). Each `--init-sql` file is then applied in order, with `ON_ERROR_STOP`, through the same retry.
4. Runs `<command>` with `DATABASE_URL` and `CLAUDE_RUN_TEST_DATABASE_URL` set to the throwaway Postgres and `CLAUDE_RUN_TEST_POSTGRES_CONTAINER` set to the container name, inheriting stdio, and propagates its exit code (128 + signal if it was killed by one).
5. Stops the container on normal exit, on command failure, on SIGINT/SIGTERM, and on any error in steps 2-3. A teardown failure is reported and makes the exit code non-zero even when the command itself succeeded.

The password never appears in a log line or an error message.

## Using it

- `just test-postgres` runs `cargo run -- test-postgres -- cargo test`, the recipe for this repo's own Postgres-backed suite. Each test fixture clones a per-process template database with `CREATE DATABASE ... TEMPLATE` rather than replaying the migration set (SPEC-5.6, CLAUDE-540), so the leg is cheap enough to run at high parallelism. This repo's own CI runs its Postgres leg through this subcommand with `--network` set to the job container's network (`.forgejo/workflows/check.yml`, SPEC-11.1, CLAUDE-543): the job is a container on its own network, so a port published on the Docker host is out of its reach. CI narrows the leg to the DB-touching files (`scripts/postgres-test-filters.txt`); `just test-postgres` runs the whole suite locally, which is harmless since the non-DB tests just repeat their SQLite-leg work.
- When the caller is itself a container sharing a Docker network with the daemon (this repo's CI, or a local-dev or other-repo setup), pass `--network <name>`: the container joins that network and is reached by name on 5432 instead of the Docker host loopback, and the subcommand probes reachability over that URL and fails fast naming `--network` if it cannot connect, rather than letting every test time out on its pool (CLAUDE-541).
- In another repo, the same binary and the same pattern apply, e.g. `claude-run test-postgres --init-sql scripts/test-db-roles.sql -- cargo test` for a suite that needs extra roles set up first.
- `deploy/bot-CLAUDE.md` tells the agent to use this subcommand and never point `DATABASE_URL` / `CLAUDE_RUN_TEST_DATABASE_URL` at any other database.

## Why not a shared service

A Postgres service in `compose.yml` was considered and rejected: it would be one long-lived server shared by every session, the test harness never drops its schemas, and parallel runs would share it. Telling the agent to `docker run postgres` itself was also rejected: the cleanup, the settings, and the image choice would then be reinvented (and inconsistently cleaned up) by every run.
