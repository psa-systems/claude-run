# Throwaway test Postgres (CLAUDE-404)

`claude-run test-postgres [--image <ref>] [--init-sql <file>]... [--network <name>] -- <command> [args...]` is how an agent session (or anyone else) runs a Postgres-backed test command: it starts a private, non-durable Postgres container in the Docker-in-Docker sidecar every agent session already has, runs `<command>` against it, and tears the container down however the command ends. CLAUDE-403 stopped the `claude` child from reaching the runner's own live database, which otherwise left Postgres-backed suites (claude-run's own `CLAUDE_RUN_TEST_DATABASE_URL` pass, and other repos' suites that read `DATABASE_URL`) unverified until CI; this subcommand is the replacement.

## What it does

1. Sweeps orphaned containers first: any earlier `claude-run-test-postgres-*` container labelled `claude-run.test-postgres=<pid>` whose owning pid is no longer alive is stopped, since containers started by hand are not reliably removed.
2. Starts `docker run --detach --rm` with a loopback-only ephemeral publish (`--publish 127.0.0.1::5432`, the port read back with `docker port`), or with `--network <name>` on that Docker network with nothing published, reached by container name on port 5432, `--shm-size 256m`, `--memory 4g`, and a random per-run password. The default image is `docker.io/postgres:18.4-alpine3.23`; `--image` overrides it so a repo whose CI pins a different tag (app-server uses `postgres:18.2-alpine3.23`) can match it. No tmpfs, no volume: the container's own writable layer is discarded by `--rm`, and the data directory is never put on the host's RAM-backed tmpfs (a large suite, about 1,300 cloned databases in app-server, can fill it).
3. Waits for a `psql` connection to succeed (up to 60s), over the same unix socket path every later step connects through, rather than `pg_isready`: the official postgres image's entrypoint restarts the server once after its own `initdb`, and `pg_isready` can report ready during the brief window before that restart, which is no guarantee that `psql`'s own connection succeeds. Then disables durability (`fsync`, `synchronous_commit`, `full_page_writes` all `off`, reloaded with `pg_reload_conf()`, verified by reading `SHOW fsync` back) since a throwaway database does not need to survive a crash: app-server measured this cutting a 229-migration run from 1.12-1.32s to 0.60-0.71s. Both the settings change and the `SHOW fsync` read-back retry for up to 20s against a connection failure that looks like that restart (the "starting up" / "shutting down" messages, or the unix socket going missing mid-restart), logging the first such retry at `warn`; a failure that does not look like a restart, or one still failing once the window elapses, fails the run immediately. Before that, it opens a TCP connection to the URL it will hand the command, from its own process, for up to 20s: `psql` answering inside the container says nothing about whether the command can reach it. A caller that runs in a container of its own (a CI job) cannot reach the Docker host's loopback, so without `--network` it would get a URL that never answers and every test would time out on its pool (CLAUDE-541); this check fails within seconds instead and names `--network`. Each `--init-sql` file is then applied in order, with `ON_ERROR_STOP`, through the same retry.
4. Runs `<command>` with `DATABASE_URL` and `CLAUDE_RUN_TEST_DATABASE_URL` set to the throwaway Postgres and `CLAUDE_RUN_TEST_POSTGRES_CONTAINER` set to the container name, inheriting stdio, and propagates its exit code (128 + signal if it was killed by one).
5. Stops the container on normal exit, on command failure, on SIGINT/SIGTERM, and on any error in steps 2-3. A teardown failure is reported and makes the exit code non-zero even when the command itself succeeded.

The password never appears in a log line or an error message.

## Using it

- `just test-postgres` runs `cargo run -- test-postgres -- cargo test`, the recipe for this repo's own Postgres-backed suite.
- In CI, where the job is itself a container on a per-job network, pass that network: `claude-run test-postgres --network <job network> -- cargo test` (`.forgejo/workflows/check.yml` does).
- In another repo, the same binary and the same pattern apply, e.g. `claude-run test-postgres --init-sql scripts/test-db-roles.sql -- cargo test` for a suite that needs extra roles set up first.
- `deploy/bot-CLAUDE.md` tells the agent to use this subcommand and never point `DATABASE_URL` / `CLAUDE_RUN_TEST_DATABASE_URL` at any other database.

## Why not a shared service

A Postgres service in `compose.yml` was considered and rejected: it would be one long-lived server shared by every session, the test harness never drops its schemas, and parallel runs would share it. Telling the agent to `docker run postgres` itself was also rejected: the cleanup, the settings, and the image choice would then be reinvented (and inconsistently cleaned up) by every run.
