# Merge and automerge

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## PR merge deliveries (CLAUDE-277)

CLAUDE-277 closes a CI-failure issue on merge, for a workflow (like app-server's PR-only `integration.yml`, DEV-612) that never runs on `default_branch` and so never satisfies a green-on-`main` polling check. `/webhooks/forgejo/<source>` (`forgejo_webhook`, `src/web/webhooks.rs`) now dispatches on the delivery's `X-Forgejo-Event` header BEFORE parsing: `pull_request` deliveries deserialize a new `PullRequestPayload` and dispatch onto a second channel (`VerifiedPullRequestEvent`, drained by `consume_pr_events`, mirroring `consume_events`); an empty header or one starting `action_run_` keeps the pre-existing Action-run parse path; anything else is acked (200) and dropped. Every gate the Action-run path runs (signature, replay, rate-limit, pause, allow-list) applies identically, ahead of the dispatch. Only a terminal `action: "closed"` delivery does anything (`handle_pull_request_delivery`): `merged: false` marks the PR's own `agent_pull_requests` row `closed` via `store::set_agent_pr_state` (a human's PR, with no row, changes nothing); `merged: true` (`handle_merged_pr`) marks that row `merged` and returns, with no tracker call and no forge run-list call. CLAUDE-327 removed the rest of what this bullet used to describe: the runner no longer decides whether a merged PR's issue is green enough to close. A YouTrack workflow (`docs/yt-workflow-resolve-on-pr-merge.js`, attached per-project by an operator) resolves any issue whose own PR merges, matching by title token, a bare `#KEY-N` line, or a `Closes KEY-N` line in the PR body, and does so for every issue with a linked PR, not only ones the runner minted. `Forge::pr_referenced_issues`, `CommitRunsClient` / `CommitRun` / `parse_runs_list_commits` (`src/forge_log.rs`, `src/provider/cli.rs`), `src/ci_failure/close.rs` (`latest_run_at_commit`, `is_green`), and `MintContext.commit_runs` are all gone; `mint.resolved_state` (`MintConfig`, still defaulting `Done`) is now read-only, consulted at CI-failure match time (see the CLAUDE-327 bullet below) rather than written by a close path. `WebhookState` still carries the `Option<mpsc::Sender<VerifiedPullRequestEvent>>` behind a `with_pr_events` builder (not a `new`/`from_shared` constructor parameter, so every pre-existing call site - including `comment_webhooks`'s cross-listener replay-store test - stays source-compatible); `None` (no daemon wiring, every pre-CLAUDE-277 test) acks and drops a `pull_request` delivery with a log, the same degrade `mint: None` already gives a `pull_request` event with nowhere to go. The `X-Forgejo-Event` header name and its `action_run_failure` / `action_run_success` / `action_run_recover` / `pull_request` values follow the SAME Gitea-to-Forgejo rebranding pattern the existing `X-Forgejo-Signature` / `X-Forgejo-Delivery` headers already use and the notifier doc comment on `VerifiedFailureEvent::status` already cites; an operator must still confirm it against their deployed Forgejo's actual delivery (see the operator-setup note in [docs/webhooks.md](../webhooks.md)) before the second event type does anything.

## Event-driven automerge (CLAUDE-278)

CLAUDE-278 replaces the CLAUDE-126 automerge poll with an event-driven one, after GAMMA-1174 recorded "Automerge timed out after 300s waiting for the PR's CI checks to pass" on a suite (app-server's integration tests) that runs longer than any reasonable job-slot budget. `finalize` (`src/native/youtrack.rs`) no longer waits for CI at all: the `if src.automerge.enabled { automerge(...) }` block that used to poll `forge.pr_status` in a loop is gone, along with the loop itself (`automerge`, `sleep_with_cancel`) and the now-unreachable `Finalized::Merged` variant - a successful run always stops at Code Review immediately, whether or not automerge is enabled. What survives from the old poll loop is only the terminal write sequence on green, pulled out into `pub(crate) fn complete_automerge` (merge as a merge-commit, then a best-effort comment; CLAUDE-327 removed its `State`/`AI Agent` write, since the YouTrack workflow resolves the issue once it observes the merge, not the runner) - the ONE shared function both the old code path used to inline and the new caller below now calls. The new caller is the webhook: `forgejo_webhook` (`src/web/webhooks.rs`) no longer drops every `action_run_success` / `action_run_recover` delivery as "non-failure action" - `payload.action == "success" || "recover"` now routes to `handle_action_success`, which allow-list-checks the repo and emits a `VerifiedActionSuccessEvent` (repo, commit sha, html_url, source) onto its own channel, drained by `consume_action_success_events`/`process_action_success_event` (mirroring `consume_pr_events`'s shape: one task per event, a `(repo, pr)` `KeyGate` key, a `run_events`-recorded webhook run). `handle_action_success_for_pr` is the actual decision: find the open PR matching the run's commit (`pr_matching_commit`, reused from the CLAUDE-276 routing), look it up in `agent_pull_requests` (`store::agent_pr`; anything not `state == "open"` is left alone), load THAT PR's own action off disk (`crate::action::load(&row.action_name, paths.actions_dir())`) to check `automerge.enabled` (an action that no longer exists, or isn't a youtrack action, or has automerge off, is also left alone), then read `forge.pr_status`: anything not `success` does nothing, because a later `success` event is what retries, for as long as CI takes (a real failure is the existing CI-failure webhook's job, not this one). `automerge.wait_seconds` / `automerge.check_interval_seconds` (`src/action.rs`) are now dead weight kept only for back-compat: still parsed (so a deployed action file keeps loading), but `validate_native` warns once at load when either is set away from its default, naming them deprecated. Operators must add Action Run Success and Recover to any webhook backing an automerge-enabled action, alongside Failure (see "Event-driven automerge" in [docs/webhooks.md](../webhooks.md) and its operator-setup note, and the migration note above it).

## Automerge reconciler (CLAUDE-328)

CLAUDE-328 gives the CLAUDE-278 webhook path a reconciler backstop, because several of its exit paths were silent (`warn!`/`info!` only, no `run_events` row, no issue comment) and the mechanism itself was a single point of failure: a missed, dropped, or too-early Action Run Success/Recover delivery left a green, mergeable PR stuck at Code Review with nothing watching it and no operator-visible signal. `handle_action_success_for_pr` (`src/web/webhooks.rs`) is now a thin wrapper around a new shared decision function, `apply_automerge_decision(mint, pool, host, repo, pr_number, pr_url, row)`, which owns the whole `pr_status` read plus the `behind_base` / mergeable dispatch (unchanged from CLAUDE-278/CLAUDE-309), calling `complete_automerge` with no `State` or `AI Agent` write from either entry point (CLAUDE-327). A new `reconcile_automerge` function calls the exact same `apply_automerge_decision` for every `agent_pull_requests` row with `state = 'open'` (`ci_failure::store::open_agent_prs`, a plain `SELECT ... WHERE state = 'open'`, no schema change), skipping any whose action fails to load, isn't a `youtrack` action, or has automerge disabled. `src/daemon.rs`'s `automerge_reconciler_loop` ticks it every `AUTOMERGE_RECONCILE_TICK_SECS` (300s, alongside the scheduler's 5s and the GC sweeps' 3600s cadences), acquiring the same `(repo, pr)` `KeyGate` the webhook path uses so the two never race the same PR. Both entry points are proven to agree by a unit test (`webhook_and_reconciler_agree_on_every_decision_shape`) that drives green+mergeable, green+behind-base, green+not-mergeable, and not-green through both and asserts identical recorded backend call sequences. Every fault along either path that concerns a recorded, automerge-enabled PR - a forge-host lookup failure, a `list_open_prs` failure, a failed action load, a failed `pr_status` call, a failed merge or branch update - now logs at `error`, writes a `run_events` row, and posts a PR comment naming the failure, instead of the old quiet `warn!`; a fault that surfaces before a specific PR is even resolved (e.g. `list_open_prs` failing for the whole repo) fans out that same treatment to every open, automerge-enabled PR on the affected repo (`notify_agent_prs_of_repo_fault`), since the payload's `repo` field is the only thing known at that point. The webhook remains the low-latency path; the reconciler is strictly a backstop, and its pass is idempotent, since a PR that isn't yet green is left exactly where the webhook path would have left it. CLAUDE-331: `apply_automerge_decision` marks the `agent_pull_requests` row `merged` when `pr_status` reports `merged` and after `complete_automerge` succeeds, so a merged PR leaves `open_agent_prs` instead of being re-walked (and given a `run_events` row) every tick when the `pull_request` webhook never arrived. CLAUDE-333: the `pr_status failed` message is prefixed with `PR <repo>#<n>: `, and `apply_automerge_decision` reads the previous `run_events` message carrying that prefix (`state::run_events_last_message_containing`) before recording the new one, so an identical, recurring failure (e.g. `fj` `no commits in pr`) still logs at `error` and writes a `run_events` row every tick but posts the issue comment only once; a changed message comments again. CLAUDE-334: `reconcile_automerge` lists the forge's open PRs once per `(host, repo)` (`list_open_pr_numbers`) and marks a row `closed` when its PR is not listed, without a `pr_status` call, because `fj pr status` fails (`no commits in pr`) for a PR closed without merge and left the row retried every tick; a failed listing logs at `error`, writes a `run_events` row, and leaves that repo's rows `open`. CLAUDE-365: a listing failure otherwise had no visible end, so a fault an operator saw once looked identical to one still ongoing; `reconcile_automerge` now takes an in-memory `listing_failures: &mut HashMap<(host, repo), u32>` (owned by `automerge_reconciler_loop`, so a daemon restart starts empty and never reports a false recovery for a fault that predates it) that counts consecutive failures per `(host, repo)`, and the first later pass on which that pair's listing succeeds removes the entry, logs at `info`, and writes an `info` `run_events` row reading `automerge reconciler: list_open_prs for <repo> recovered after <n> failed pass(es)`. CLAUDE-397: `apply_automerge_decision` returns a typed `AutomergeOutcome` (`NoAction` or `Acted`) instead of a bare summary string, and `reconcile_automerge` opens a `webhook-triage` `runs` row only for `Acted` or `Err`; a `NoAction` pass (checks not green, automerge disabled, the action isn't a youtrack action, or not mergeable) leaves only its existing `info` log line (and, for not-mergeable, its existing `run_events` row), so the 300s sweep over every open agent PR no longer writes one `runs` row per PR per pass regardless of whether anything changed. `handle_action_success_for_pr` (the webhook delivery path) still maps either variant to its summary string, so its own recorded run and summary are unchanged.

## Behind-base PRs (CLAUDE-309, FJ-99)

CLAUDE-309 (depends on FJ-99) fixes the `success` branch above: Forgejo's `mergeable` never covers being behind the base branch, so the old green-but-behind-base check (`!mergeable`) actually meant a real conflict, a still-checking PR, or a WIP PR, and a green+`mergeable` PR that was simply behind its base raced straight into `merge_pr`'s 405 refusal. `PrStatus` (`src/provider/mod.rs`) gained `behind_base: Option<bool>` (`#[serde(default)]`, threaded through `CliBackend::pr_status`'s `fj pr status --json` parse), and the decision in `handle_action_success_for_pr` now branches on it first: `None` (an `fj` predating FJ-99) takes no merge action, comments `automerge_behind_base_missing_comment`, and fails the run so a stale deployment is visible rather than silently never automerging; `Some(true)` calls the new `Forge::update_pr_branch` (`CliBackend` runs `fj pr update <repo>#<n> --style merge`, FJ-99's Update-branch endpoint) instead of merging, commenting `automerge_branch_updated_comment` on success or `automerge_update_failed_comment` on failure (and failing the run in the latter case); `Some(false)` with `!mergeable` comments the reworded `automerge_not_mergeable_comment` (conflict/checking/WIP, no longer claiming "behind base"); `Some(false)` and mergeable is the unchanged `complete_automerge` path, now also commenting `automerge_merge_failed_comment` and failing the run on a merge error instead of swallowing it. `Forge::update_branch` (the old git-workdir merge-base-into-head-and-push helper `finalize` could never reach from the webhook) is deleted along with `CliBackend`'s implementation; every failure-path comment is posted through the new best-effort `post_issue_comment` helper (logs at `error` on a comment failure, never overriding the caller's own `Result`).

## Automerge conflict auto-resolve (CLAUDE-380)

CLAUDE-380 covers the one `Some(true)` (behind base) outcome the CLAUDE-309 bullet above leaves as a dead end: `update_pr_branch` failing because the branch and its base now conflict, which used to always comment `automerge_update_failed_comment` and name the PR "a human needs to resolve this" even though a human's own `/claude merge from main and resolve any merge conflicts` PR comment is the exact fix. `apply_automerge_decision`'s `update_pr_branch` failure arm (`src/web/webhooks.rs`) now calls `try_dispatch_conflict_auto_resolve` first: if the error text contains "conflict", the PR's `pr_status` reported a `head_sha` (CLAUDE-380 added that field to `PrStatus` and `CliBackend::pr_status`'s `fj pr status --json` parse), and a comment-webhook source's `allowed_repos` covers this repo, it sends a synthetic `VerifiedCommentCommand` (`synthetic: true`, `kind: Run { instruction: "merge the base branch into this PR's branch and resolve any merge conflicts" }`) onto the SAME channel a human's PR comment would land on, so it runs through the exact same `serve_command` pipeline (readiness, `KeyGate`, `admit`, the daily cap, the decision gate) with only the commenter-permission check skipped (`VerifiedCommentCommand::synthetic`, checked by `requires_permission_check`). The dedupe is the comment pipeline's own shared attempt counter: the synthetic command's `comment_id` is a negative hash of `(repo, pr_number, head_sha)` (`synthetic_conflict_comment_id`, forced negative so it can never collide with a real, positive Forgejo comment id), so `command_key` and `state::attempts_get`/`attempts_increment` bound the dispatch to at most one attempt per head commit, exactly like a redelivered human comment; a second conflict failure for a head commit that already has a recorded attempt falls straight back to `automerge_update_failed_comment`. The daemon wires this up by cloning `comment_tx` (`src/daemon.rs`) before it moves into `CommentWebhookState::from_shared`, bundling that clone with the live `CommentWebhookConfig` handle into `MintContext::comment_dispatch` (a new `CommentDispatch { tx, cfg }`, `None` in every test and in any daemon run with the comment listener unconfigured, which keeps the pre-CLAUDE-380 behavior exactly). A successful dispatch comments `automerge_conflict_resolving_comment` ("The runner is attempting to resolve the conflict automatically") instead of the human-needed comment for that one pass; a non-conflict error, a missing `head_sha`, no wired `comment_dispatch`, no comment-webhook source covering the repo, or a channel send failure all fall back to the pre-existing comment and are logged accordingly (`run_events`, `error`/`info`), never silently swallowed.

## GitHub automerge (CLAUDE-405)

CLAUDE-405 implements `pr_status` / `merge_pr` / `update_pr_branch` on `GithubForge` (`src/provider/github.rs`), the three operations `resolve_automerge_forge` (`src/web/webhooks.rs`, CLAUDE-357) already routed a `github.com`-hosted PR to but which previously fell through to the `Forge` trait's default "not supported by this forge backend" error. `pr_status` runs `gh pr view <n> --repo <repo> --json state,mergeable,mergeStateStatus,headRefOid,statusCheckRollup`: `state` is `"merged"`/`"closed"` from GitHub's own PR state, or derived from `statusCheckRollup` otherwise (any failed check wins, else any still-running check is `"pending"`, else `"success"`; an empty rollup is `"pending"`, never a green default); `mergeable` and `behind_base` map from GitHub's `mergeable` and `mergeStateStatus` enums, with every unrecognised value an error naming it rather than a guessed default. `merge_pr` runs `gh pr merge <n> --merge --delete-branch` (merge-commit, matching the Forgejo path's `--method merge --delete`); `update_pr_branch` runs `gh pr update-branch <n>` (merge-style, GitHub's endpoint has no rebase mode), whose conflict failure carries `gh`'s stderr through `Error::CliFailed` unmodified so `try_dispatch_conflict_auto_resolve`'s "conflict" text match (CLAUDE-380) still fires on GitHub. No change to the Forgejo path or to `apply_automerge_decision`/`complete_automerge`, both already generic over the `Forge` trait. `pr_status` needs a classic PAT with the `repo` scope: a fine-grained PAT cannot read the check runs in `statusCheckRollup` (GitHub has no fine-grained permission for them) and every call fails with `Resource not accessible by personal access token (...statusCheckRollup...contexts.nodes.N)`. `resolve_forge` builds `GithubForge` with no token, so the token automerge uses is the daemon's own `gh` login from Settings -> Auth (`auth-github-token`), read on every pass; the action's `github.token_ref` and a webhook source's `write_token_ref` are separate secrets it does not read.

## Naming the right cause for a missing behind_base (CLAUDE-421)

`PrStatus.behind_base` is `None` for two unrelated reasons, and `apply_automerge_decision` (`src/web/webhooks.rs`) names the one that applies by branching on `is_github_host(host, &github_cfg.hosts)`. On a Forgejo host it means `fj pr status` did not report the field (an `fj` predating FJ-99), a stale deployment a human must fix, and the log line, `run_events` message and `automerge_behind_base_missing_comment` say so. On a GitHub host it means `gh pr view` reported `mergeStateStatus: UNKNOWN` (`GhPrStatusDoc::into_pr_status`, `src/provider/github.rs`): GitHub computes mergeability lazily, so a freshly pushed or updated PR reports it until the computation finishes. That state is transient, `fj` is not involved, and the message and comment say the runner re-checks on the next reconciler pass and that no action is needed unless it persists. Both causes take no merge action and fail the run, and both still go through `record_automerge_outcome_and_comment_once` (comment once per unchanged outcome, a `run_events` row every pass). `UNKNOWN` is never treated as "not behind", because it carries no information.

## State on merge is a YouTrack workflow (CLAUDE-327)

CLAUDE-327 removes the runner's own `State`-on-merge writes and hands that job to a YouTrack workflow, because the CLAUDE-277 close path (a `CommitRunsClient` paging loop to find the merged PR's head-commit run and decide green) only ever resolved an issue the runner itself had minted, and asking it to resolve every issue in a project would have meant teaching the runner to find and evaluate a PR-owning issue with no forge run in its own history at all. `docs/yt-workflow-resolve-on-pr-merge.js` is attached per-project by an operator (see the operator-setup note in [docs/webhooks.md](../webhooks.md)) and resolves any issue whose linked PR just merged, matching by title token, a bare `#KEY-N` trailer line, or a `Closes/Fixes/Resolves KEY-N` line in the PR body, the same tail `mint::build_description` already writes. `handle_merged_pr` (`src/web/webhooks.rs`) now only flips its own `agent_pull_requests` row to `merged`; `complete_automerge` (`src/native/youtrack.rs`) only merges and comments. Because the store's `open`/`resolved` column no longer changes on merge, an `open` `ci_failures` row can still name an issue the workflow already resolved by the time a later CI failure on that same test set is triaged, so both CI-failure dispatch sites (`triage_and_mint`'s no-open-PR path and `route_human_pr_failure`) now read the issue's live `State` at match time (`issue_state_is_resolved`, `IssueTracker::get_field(key, "State")` compared to `mint.resolved_state` case-insensitively) before deciding: equal means a regression, so `reopen_resolved_failure` runs unchanged; not equal is the ordinary open-and-still-open attach; a read failure fails the run (an `error` log, a `run_events` row, no comment or attach) rather than risking a false attach on a state it could not confirm.
