# State store and config

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## State store backend (CLAUDE-250)

The state store is SQLite or PostgreSQL, chosen by the operator (CLAUDE-250). `src/db.rs` opens ONE `sqlx::AnyPool` (`db::DbPool`) for either, so no module outside it names a backend type, and it holds the two migration sets: `migrations/sqlite/` is the original twenty files, byte-identical so a deployed `state.db` matches its recorded checksums and re-runs nothing, and `migrations/postgres/0001_init.sql` is a hand-written squash of their end state (`BIGINT` for every integer, `DOUBLE PRECISION` for `REAL`, `BYTEA` for `BLOB`, `GENERATED BY DEFAULT AS IDENTITY` for the autoincrement keys, boolean-ish columns left as integer 0/1). `Any` forwards SQL unchanged, so `db::q` is the chokepoint every statement passes through: it renumbers `?` / `?N` into `$n` for Postgres and expands the two dialect-neutral functions the call sites are written in, `strpos(haystack, needle)` and `elapsed_seconds(from, to)`. Everything else is spelled portably in place (`COALESCE`, `ON CONFLICT DO NOTHING`, `CAST(... AS BIGINT)` around a `SUM()` over an integer, `<table>.<col>` on the right of a `DO UPDATE SET`, no negative `LIMIT`), and integer 0/1 columns decode through `db::flag` because `Any` will not coerce an integer to a `bool`. Selection is a bootstrap key, not a DB-backed setting: `[database] url`, overridden by `CLAUDE_RUN_DATABASE_URL`, overridden by the contents of the file named by `CLAUDE_RUN_DATABASE_URL_FILE`. Unset is SQLite; an unknown scheme or an unreachable server stops the daemon rather than falling back. `compose.yml` carries `claude-bot-postgres` behind a `postgres` profile. Setting `CLAUDE_RUN_TEST_DATABASE_URL` re-runs the WHOLE test suite against Postgres (one schema per fixture pool), which is what CI does after the SQLite pass. See README "State store backend". A schema change is a new incremental file in EACH migration directory (e.g. `migrations/sqlite/0021_ci_failures.sql` plus `migrations/postgres/0002_ci_failures.sql` for the CLAUDE-272 CI-failure store), with the same end schema on both sides; the twenty original SQLite files, and any shipped since, stay byte-identical.

## Backend import (CLAUDE-251)

Switching backends carries the data over with `claude-run import` (CLAUDE-251, `src/import.rs`). Selecting Postgres only opens an empty instance, and the data that would be lost is not disposable: `secrets` holds the ciphertext for the web token, the webhook HMACs and the service logins, `web_admin` the argon2id hash and the session key, and `attempt_counters` / `daily_ledger` are what stop a job being retried past its cap. The copy is schema-driven, not typed per column: the source's own `pragma_table_info` gives the column list and the declared type that decides the Rust type each value round-trips as (SQLite affinity is what makes that sound), so a migration that adds a column needs no edit here. The target is whatever `config::resolve_database` resolved, never a flag of its own, so the import and the daemon cannot disagree about where the rows went. `import::TABLES` is the hand-maintained foreign-key order and is compared against the live catalog on every import (and by `the_table_list_matches_the_schema`), so a new table fails the copy instead of being silently left behind; `IDENTITY_COLUMNS` is the four Postgres sequences advanced past the copied ids, without which the daemon's first insert collides with imported history. The source is opened `mode=ro` and never written, the whole copy is one transaction, a target holding rows is refused unless `--allow-nonempty`, and per-table source/copied/target counts are printed and checked before the commit rather than a bare success line. A source older than the build is refused naming every missing column, because a read-only open cannot apply the pending SQLite migrations.

## Bootstrap vs runtime config (CLAUDE-101)

Config splits into bootstrap vs runtime settings (CLAUDE-101). `config.toml` holds only bootstrap keys the daemon needs before it can open the DB and bind: `[database] url` (CLAUDE-250), `[web]` and `[daemon]` binary overrides (`nu_binary`, `claude_binary`). Everything runtime-tunable is DB-backed (one JSON document per section in the `settings` table, keyed `config.<section>`) and edited on the web Settings page (`/settings`) or via `GET`/`PUT /api/settings/<section>`. The DB-backed sections are `config.mint`, `config.update`, `config.webhook`, `config.webhook_comment` (CLAUDE-220), `config.log_filter`, `config.workdir_gc`, `config.stream_log_gc` (CLAUDE-245, extended to the whole `logs/` tree by CLAUDE-257), `config.preferences`, `config.concurrency`, `config.db_retention`, and `config.claude` (CLAUDE-239: the global default `--model`, which an action's own `claude.model` overrides; CLAUDE-259 added `effort` on the identical precedence, with the documented set `low | medium | high | xhigh | max` advisory only, so an unrecognized level is warned about once and then passed through rather than rejected or substituted; DEV-706 added `autocompact` on the same precedence, except that its last step is the runner's own bounded default rather than no flag). The first four of those (`[mint]` / `[update]` / `[webhook]` / `[daemon].log_filter`) were moved out of `config.toml` and carry the one-time import; the rest are DB-only from birth and have no import path. The serde structs in `src/config.rs` stay the schema; `src/settings.rs` owns the store, the live-apply (`LiveSettings`), and the one-time import then breaking-on-conflict migration (`migrate_config_file`, run at serve start). A moved section present in both `config.toml` and the DB refuses to start, naming it, and `[webhook_comment]` is rejected by the file parser outright (it is absent from `OnDiskConfig`).

## Global pause (CLAUDE-223)

Global pause is one DB flag (`global_pause`, `src/state.rs`) honoured at EVERY entry point (CLAUDE-223): the scheduler tick, `Dispatcher::execute`, the daemonless `claude-run run`, the trigger endpoint (`409` naming the pause, not a lying "queued trigger" ack), both webhook listeners (accept-and-drop with `2xx`, via the shared `webhooks::paused_accept_and_drop`), the automerge reconciler tick and the queued action-run success consumer (CLAUDE-332, `webhooks::webhook_action_paused(pool, action, what)`: global pause or the named synthetic action's pause, and an unreadable flag skips rather than acts; CLAUDE-335 runs it at the top of every per-event task in `consume_events`, `consume_pr_events` and `comment_webhooks::consume_commands`, the last against `webhook-forgejo-comment`), and the per-job checkpoints of every runner. That last one is `src/pause.rs`: a TTL-cached `PauseGate` (daemon-wide, refreshed each scheduler tick, so a blocking checkpoint can read the last value with no `await`) plus a run-scoped `RunPause` that records whether the pause actually stopped work. A run it stopped finishes with `exit::PAUSED` (1), badged "paused" and distinct from an operator cancel (130); its unprocessed jobs consume no attempt. A failed gate read is logged at `error` and treated as NOT paused, so a transient DB error cannot silently stop the daemon. The operator surface is the Activity card on `/about` (Pause / Resume plus a 2s-polled busy / idle / unknown indicator, `templates/activity.html` + `GET /about/activity`); `unknown` is a distinct state precisely so a failed activity query never reads as "safe to restart". The same snapshot is on `/api/status` as the `activity` block. See README "Global pause and the restart-safety workflow".
