# CI failures and webhooks

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

## CI-failure store (CLAUDE-272)

CLAUDE-272 added the CI-failure store: `ci_failures` (one row per distinct failure, keyed on `(repo, workflow_id, job_name)`, nullable `issue_key` because a failure seen only on a human's PR has no issue), `ci_failure_tests` (its failing-test fingerprint, unique per `(failure_id, test_id)`), `ci_failure_runs` (one row per sighting: commit, branch, PR number, timestamp), and `agent_pull_requests` (every PR the runner's own `youtrack` action opens, unique per `(host, repo, pr_number)`, carrying `fix_attempts` so a re-queued issue is recognised as a continuation). The new module `src/ci_failure/` holds `fingerprint::{failing_tests, fingerprint}` (pure string parsing of cargo test output, no LLM, no I/O, modelled on `src/infra_failure.rs`; falls back to `mint::failure_signature` when nothing cargo-shaped parses) and `store` (the async functions over `DbPool`, notably `find_match`, which answers "which issue does this failure belong to" by test-id overlap within the same repo/workflow/job, preferring `open` over `resolved` over `pr_only` and the newest on a tie). `ci_failure_runs` joins `RETENTION_TABLES` (`src/retention.rs`) since it is per-sighting history; the other three tables are never pruned, because a resolved failure or a merged PR must still match a regression months later. `agent_pull_requests` is wired into the `youtrack` action by CLAUDE-275 (below); CLAUDE-273 (below) wires `ci_failures` / `ci_failure_tests` / `ci_failure_runs` into the webhook.

## Re-queued issues continue their PR (CLAUDE-275)

CLAUDE-275 wires the `agent_pull_requests` store into the `youtrack` action so a re-queued issue continues its own open PR's branch instead of opening a second one. `PullRequest` (`src/provider/mod.rs`) gained `head_branch: Option<String>`, filled in by `CliBackend::create_pr`'s branch strategy and by `GithubForge::create_pr` (both always branch-backed) with the branch just pushed; the AGit strategy leaves it `None`, since `refs/for/<base>` produces no server branch. `process_job` (`src/native/youtrack.rs`) looks up `store::agent_pr_for_issue` before `pre`: an `open` record is confirmed live against `Forge::list_open_prs`, and when still open its `head_branch` is what `run_pre` clones instead of the default branch, with `{{existing_pr_url}}` / `{{existing_branch}}` (new prompt placeholders, empty on a fresh pickup) telling the agent to fix that same branch rather than open another. A record absent from the open list is marked `closed` (merged and closed are not distinguishable from an open-PR listing alone) and pickup falls back to the default branch as before; the AGit strategy always skips resume (logged at `info`), since it has nothing to resume onto. `finalize` cannot make the store's async write itself - it is a synchronous state machine whose own unit tests run with no tokio runtime - so `Finalized::CodeReview` carries `pr_number` / `head_branch` out and `process_job` calls `store::record_agent_pr` right after `finalize` returns, but ONLY on a non-resumed success: re-recording a resumed PR would collide with the store's `UNIQUE(host, repo, pr_number)`. A failed record write logs at `error`, reaches `run_events` through a new `Forge::note` default-no-op method (`CliBackend` pushes it onto the same notice queue `take_notices` already drains), and gets a follow-up issue comment naming it, none of which fail the job: the PR already exists and the issue already sits at Code Review. `run_pre`'s resume clone pins that `head_branch` into `provider::shallow_clone`, and CLAUDE-311 makes that pinned clone also fetch the remote's default branch and set `origin/HEAD`, because `CliBackend::resolve_feature_branch`'s base-branch resolution depends on it.

CLAUDE-467 extends the same resume onto a push or PR-create failure, which used to park the issue at a terminal `Failed` even when the work was already safe on the remote or recorded against an open PR. `finalize`'s PR-failure branch (`src/native/youtrack.rs`) now takes `resume_pr_url`, this issue's recorded PR at finalize time (the CLAUDE-275 lookup above, or one the CLAUDE-448 checkpoint-push watcher below adopted mid-run); with that PR recorded and the attempt count below `max_attempts_per_key`, it re-reads the `AI Agent` field (the same re-read-before-stomp the Working-to-Queued reverts below use), and when it is still `Working` posts a comment naming the cause and the PR, sets `AI Agent = Queued`, and returns `Finalized::Failed { requeued: true, .. }` so the attempt is still counted and run history shows it was requeued rather than a plain failure. With no recorded PR, at the cap, or with the field already advanced off `Working` by requeue time, it is left exactly as before: `requeued: false`, `Failed`, no field write when already advanced.

## Timeout salvages work as a draft PR (CLAUDE-379)

CLAUDE-379 gives a killed run (`claude_result.timed_out`, exit 124) the same PR-on-the-wire outcome a successful run gets, instead of leaving whatever the agent built stranded in a workdir that only survives until the next cleanup sweep. `finalize`'s timeout branch (`src/native/youtrack.rs`) calls `salvage_timeout_work`, which reuses `workdir::local_only_work` - the EXACT query `cleanup_or_preserve` runs - so "is there anything to salvage" can never disagree with "should the workdir be preserved": a clean tree with nothing ahead of the remote default branch salvages nothing and the timeout comment says so. Otherwise a dirty tree is committed as a single `WIP: uncommitted changes at timeout` commit (`commit_timeout_wip`, real `git add -A -- . :!.claude-run-*` then `git commit`, excluding `.claude-run-*` markers by pathspec so operator/runner state never lands in the agent's branch), then `Forge::create_pr_with_draft` pushes and opens the PR exactly like a normal finish except forced `draft: true`: the Forgejo backend prefixes the title `WIP: ` (fj's own draft convention, since `fj` has no real draft flag) and the GitHub backend passes a real `draft` field (MCP) / `--draft` flag (`gh pr create`). A comment explaining the timeout (limit, cost, whether the branch's tip is the runner's own WIP commit or the agent's, and that re-queuing resumes this branch rather than opening a second PR) is posted on the opened PR via the existing `Forge::pr_comment`, body written to a scratch file under `std::env::temp_dir()` (the only writable scratch available to a free function with no workdir of its own, `tempfile` being dev-only). Every step (reading git state, the WIP commit, the push/PR-create, the PR comment) fails independently onto its own `SalvageReport` field, is logged at `error` naming which step, and is named in the issue's timeout comment - never swallowed into one generic "salvage failed". The salvaged PR is carried out of `finalize` on `Finalized::TimedOut { pr_number, head_branch }` exactly like `Finalized::CodeReview` carries a successful one, so `process_job` records it into `agent_pull_requests` via the SAME CLAUDE-275 `record_new_pr` call (an or-pattern across both outcome variants) and a re-queue resumes onto the salvaged branch through the unchanged CLAUDE-275 resume path; the default prompt's resume step additionally tells the agent to read that PR's own comments, since a timed-out run's salvage note (what it committed, why) lives there rather than on the issue. The issue still ends on `AI Agent = needs_review` and the attempt counter still increments exactly as a timeout always did - the salvage changes what gets left behind, not the tracker-side outcome. `Forge::create_pr_with_draft` and `Forge::mark_pr_ready` are new trait methods with default bodies (fall back to the existing non-draft `create_pr` / error "not supported") rather than new parameters on `create_pr`, so no existing `Forge` implementor (including the test-only stub in `src/web/webhooks.rs`) needs to change. A later resumed run that finishes successfully calls `mark_pr_ready` to strip the draft/`WIP: ` status (`fj pr edit <id> title <stripped title>`, since `fj pr edit` has no `--title` flag; a failed promotion is logged and named in the success comment, CLAUDE-456; `gh pr ready`), so a salvaged-then-completed PR does not sit marked draft forever.

CLAUDE-398 closes three gaps this left open. First, the draft PR's body is no longer derived from the tip commit's own `%b` (either the WIP commit's empty body or an agent commit whose body is only the bare issue reference, telling a human nothing): `create_pr_with_draft` gained a `body: Option<&str>` override, and `salvage_timeout_work` builds one with `draft_pr_body(key)`, a short runner-written explanation pointing at the PR's first comment for the timeout/cost detail. Second, a tip whose subject is itself a Markdown heading (an agent mistaking its PR-description template's first line, e.g. `## Summary`, for the commit subject) no longer opens a PR titled that heading: `validate_pr_subject` (`src/provider/mod.rs`) runs before every push in every create path (branch, AGit, GitHub), rejecting a subject that starts with `#`, is empty, or exceeds a sane length, before any push or `fj`/`gh` call. Third, a resumed run that finishes no longer leaves the salvage's placeholder title/body in place forever: `Forge::refresh_pr_text(workdir, host, repo, pr_number)` (implemented on both backends, default errors "not supported") re-derives the title/body from the finished tip, runs the same `validate_pr_subject` guard, and overwrites the PR with a `fj pr edit <id> title` call then a `fj pr edit <id> body` call (a body failure after the title landed is named in the error); it is a no-op on a PR that is not actually still a draft, and `finalize`'s resumed-success path calls it alongside `mark_pr_ready`, best-effort - a failure is logged at `error` and appended to the success comment as "PR text could not be updated: ..." rather than swallowed or blocking the success outcome.

CLAUDE-429 persists the salvage provenance instead of leaving it inferable only from the draft status the paragraph above strips: `record_new_pr`'s or-pattern now also sets a `salvaged` column on the `agent_pull_requests` row (`true` for `Finalized::TimedOut`, `false` for `Finalized::CodeReview`), only for a PR salvaged after the migration that added it. The runner's automerge never acts on a flagged row, however its draft status changes; see [Salvaged PRs block automerge](merge.md#salvaged-prs-block-automerge-claude-429) for the automerge-side mechanism and the one place the flag clears.

## Checkpoint pushes open a draft PR before any timeout (CLAUDE-448)

CLAUDE-448 moves the CLAUDE-379 salvage moment earlier: instead of waiting for `claude_timeout_seconds` to open the first draft PR, `process_job` ticks a checkpoint-push watcher (`run_checkpoint_watcher`, see [the runtime mechanism](claude-runtime.md#checkpoint-push-watcher-runs-off-a-plain-os-thread-not-a-tokio-task-claude-448)) every 60 seconds for the whole time `claude` is running, pushing whatever the agent has committed so far on the feature branch with `--no-verify` (the local commit hooks only; this never touches a forge-side branch protection rule, and it is never the final push a clean finish makes). The watcher calls `Forge::checkpoint_push`, a new trait method with a default "not supported" error, implemented so far only on `CliBackend` (Forgejo via `fj`); `GithubForge` has no override yet (CLAUDE-452 tracks that as a descoped follow-up). The first push that succeeds calls `Forge::find_or_create_pr` with `checkpoint_pr_body(key)`, a short runner-written body (same `## Summary` / prose / bare `#<key>` shape as `draft_pr_body`, but describing an in-progress run and deliberately carrying no `Closes` line since the run has not finished), opens the PR as a draft, and records it into `agent_pull_requests` with `salvaged: true` via `store::record_agent_pr` directly (not through `record_new_pr`, since the watcher itself needs the new row's id to hand back to `process_job`) - unless the run is already resuming its own previously-recorded PR, in which case the write is skipped entirely, since adopting that same PR again would collide with the `UNIQUE(host, repo, pr_number)` constraint. `find_or_create_pr`'s own early return on an already-open PR for the branch means passing that body on every later tick is harmless: only the create path ever reads it, so a second or third tick on the same run's already-open PR does nothing but push and comment. Every push after the first, including the one that opened the PR, posts a `checkpoint push` PR comment through the CLAUDE-447 push-comment helper (naming the event, issue, state and SHA range like every other push-comment site). A push the forge rejects (non-fast-forward, a deleted or protected branch) is logged at `error`, stops the watcher ticking for the rest of the run - it returns rather than retrying - never fails the job over it on its own, and is named in whichever outcome comment `finalize` goes on to post (`checkpoint_push_rejected`, a new parameter threaded through all of `finalize`'s outcome branches). The default branch is never checkpoint-pushed, since `run_checkpoint_watcher` only ever pushes the job's own feature branch and does nothing at all once the branch is still empty (nothing to checkpoint yet). A run that resolves normally after a checkpoint push already opened a draft PR promotes it through the exact same CLAUDE-398/CLAUDE-429 resumed-success path a re-queued issue's PR gets, because `process_job` assigns the watcher's first opened PR into its own (now-mutable) `resume` variable the moment it is seen, with no new branching in that promotion code; a timeout after a checkpoint push already opened the PR still parks the issue on `needs_review` exactly as the CLAUDE-379 paragraph above describes (CLAUDE-453 tracks auto-requeuing that case as a further descoped follow-up).

## Failing-test dedupe (CLAUDE-273)

CLAUDE-273 moves CI-failure dedupe off a `yt` full-text search and onto the CLAUDE-272 store's failing-test overlap, and makes it unconditional: `mint::mint` (`src/mint.rs`) no longer searches YouTrack at all and never declines for a duplicate or a resolved issue - `SkippedResolved`, `SkippedDuplicateOpen`, `AssociatedWithOpen`, and `SkippedAutoFixDisabled` are gone from `MintOutcome`, and `mint` only creates once the bucket/cap gates above it pass (CLAUDE-276 later removes the open-PR and bot-loop gates from `mint` itself). The webhook consumer (`triage_and_mint` in `src/web/webhooks.rs`) fingerprints the redacted log (`ci_failure::fingerprint::fingerprint`) BEFORE triage and calls `store::find_match` against it: an `open` match calls `attach_run` / `add_tests` and comments the run + failing tests onto the existing issue with no triage and no `claude` call at all (`attach_to_open_failure`); a `resolved` match is a regression - `reopen_resolved_failure` reopens with `set_state(mint.target_state)`, posts a "Regression: ..." comment, flips the store row back to `open`, and only then runs triage so the analysis lands as a follow-up comment and `AI Agent` is set exactly as a freshly minted issue of that bucket would be (`mint::queues_for_fix`, a `pub(crate)` wrapper around the same routing table `mint::mint` uses, so the two never disagree). No match (or a `pr_only` match with no open PR on the failing commit - CLAUDE-276 routes a `pr_only` match WITH an open PR separately, before `find_match` even runs) falls through to `classify_and_mint`, which is the pre-existing triage + mint pipeline preceded by ONE legacy-adoption lookup (`decide_with_legacy_adoption`, still a plain YouTrack `#Unresolved` search on `mint::legacy_collapse_key` - the same root-cause/infra marker `mint` used to search, now `pub(crate)` and computed from plain arguments instead of a `MintRequest` it does not have yet) for an issue minted before the store existed; a `Created` outcome, or a legacy hit, is then recorded into the store (`record_new_store_row`) so the next sighting matches by test overlap rather than searching YouTrack again. A store read or write error is logged at `error` and fails the run (`ok = false`) rather than falling through to a mint, which would recreate the exact duplicate this issue removes. The webhook `auto_fix` toggle (`config.webhook.auto_fix`, CLAUDE-153) changes meaning to match: it no longer decides whether an issue is minted, only whether a `code_fix` / `auto_fix` issue's `AI Agent` gets set, so `No orphan notes` holds even with it off. The `Dedupe-Key:` / `Root-Cause-Key:` / `Branch:` / `Job:` body markers `mint::build_description` writes are UNCHANGED, because the legacy-adoption lookup above still reads it; only the searching stops. (One of the other readers at the time was retired in CLAUDE-279.)

## Single analysis pass (CLAUDE-274)

CLAUDE-274 collapses the webhook's two `claude` passes (a tool-less classifier at ingest, a separate scheduled deep analysis later) into one: `src/triage::AnalysisClassifier` runs `Read,Grep,Bash` over the COMPLETE redacted log plus the failing workflow YAML, in a per-event `webhook-logs/analysis/<owner>_<repo>-run<N>/` directory it creates and removes itself, on a timeout from the new `config.webhook.analysis_timeout_secs` (default 600). The reusable fetch/prompt/comment-formatting pieces moved out of the (now-retired, CLAUDE-279) scheduled analysis native handler into `src/ci_failure/analysis.rs` (`pub(crate)`) so both it and the at-ingest classifier shared them. The prompt ends with a fenced JSON verdict (`code_defect` | `needs_human` | `flaky` | `infra`, plus a `summary`); `triage::parse_analysis_verdict` reads the LAST balanced `{...}` object (never the first, so a Markdown code block earlier in the report cannot corrupt the span) and maps `code_defect` -> `CodeFix`, `needs_human` -> `HumanAction`, `flaky` / `infra` -> `Transient`; an unparseable or missing verdict degrades to `HumanAction` with a `warn` and never becomes `code_fix`. The session's own report becomes the `## Triage` analysis text on the minted issue, capped by `mint::build_description` at `ci_failure::analysis::DEFAULT_MAX_ANALYSIS_BYTES` (24 KiB). `consume_events` (`src/web/webhooks.rs`) no longer processes events inline: each event is spawned as its own task behind a `tokio::sync::Semaphore` sized from `config.webhook.analysis_concurrency` (default 2, validated `>= 1` in `src/settings.rs`), acquired in the receive loop so a saturated pool simply leaves later events queued in the channel; `consume_events` joins every spawned task before it returns, so a caller awaiting it (every test, and the daemon's own shutdown path) still observes each event's completed side effects. `triage_and_mint` acquires the daemon's existing `concurrency::KeyGate` (the same one `Executor` and the comment webhook already share) on `(repo, workflow_id, job_name)` before the store lookup, so two concurrent failures of the same job never both analyze: the second waits, then finds the first's store row and attaches. `ClaudeClassifier` and `TRIAGE_TIMEOUT_SECS` are deleted; the classifier is built once in `daemon::build_mint_context` with its own `Arc<dyn ForgeReads>` for the workflow-YAML fetch, and `TriageInput` gained a `log_token` field (the already-resolved `log_token_ref` secret, threaded through every call site that builds one) so the classifier can fetch the workflow YAML with the same credential that authorized the log fetch.

## Route by PR opener (CLAUDE-276)

CLAUDE-276 routes a CI failure on an open PR by who opened the PR, replacing CLAUDE-149's `mint::mint` gates (`SkippedOpenPr`, and the bot-login `is_bot_loop` check) with a lookup against the CLAUDE-275 `agent_pull_requests` store. `resolve_open_pr` (`src/web/webhooks.rs`) replaces `resolve_has_open_pr` for the routing decision: it lists the repo's open PRs and matches the failing commit's `head_sha`, but unlike the old helper (which degraded a forge error to `false`, fine only as advisory triage context) a lookup error is now returned and fails the run (`ok = false`, an `error` log), because silently reading "no PR" would send the agent's own failing PR through the create-a-new-issue path instead of re-queuing it. `triage_and_mint` resolves the PR BEFORE the CLAUDE-273 store-match dispatch, not as a fallback from it: `None` runs that dispatch (and `classify_and_mint`) exactly as before; `Some(pr)` looks it up in `agent_pull_requests` by `(host, repo, pr_number)`. An `open` row (the agent's own PR) never reaches `mint::mint` at all: below `config.webhook.agent_pr_fix_attempts` (default 3, validated `>= 1`) it comments the recorded issue (run link, failing tests, the triage analysis), bumps `fix_attempts`, and sets `AI Agent = Queued` - the exact write `youtrack`'s CLAUDE-275 pickup already resumes on; at the ceiling it sets `AI Agent = Needs Review` instead, with a comment listing every fix attempt's run (`store::run_indexes_for_failure_pr`, a new query). No row (a human's PR) always gets the analysis one way or another: sharing a failing test with an `open` `ci_failures` row gets a PR comment naming the issue and the run attached, no analysis (`route_pr_matches_open_failure`); sharing a failing test with a `pr_only` row whose sightings (`store::distinct_branches`) now span two branches promotes it to a real issue via `mint::mint` (the SAME pipeline, since the caller no longer needs to suppress it) and comments the issue link onto every PR the failure was sighted on (`store::pr_numbers_for_failure`, `mint_for_two_branch_pr_only_failure`); anything else runs the analysis, comments it on the PR, and records (or keeps) a `pr_only` row with no issue yet (`route_new_pr_only_failure` / `route_pr_matches_pr_only_failure`). A PR comment posts through a NEW per-webhook-source credential, `WebhookSource.write_token_ref` (`src/config.rs`), reaching `fj` through the same temp single-host `keys.json` mechanism `comment_webhooks::build_env` uses (`build_pr_comment_backend`, `MintContext.pr_comment_runner` - injectable so a test can supply a canned `fj` response instead of a real subprocess, mirroring `MintContext.backend`); a source with none configured is `Error::Secret`, logged at `error`, recorded as a `run_events` row naming the source (`record_run_event`, `require_pr_comment_backend`), and fails the run rather than posting nothing silently. The comment body itself is staged at a deterministic path (`pr_comment_body_path`, keyed on repo + PR number under `Paths::state_dir`) rather than inside the ephemeral, randomly-suffixed credential directory, so a test can predict it and so a repeated comment on the same PR overwrites its own scratch file. `mint::mint` (`src/mint.rs`) drops `MintOutcome::SkippedOpenPr` / `SkippedBotLoop` and the `is_bot_loop` function entirely: `has_open_pr` on `MintRequest` is now pure triage-classifier context, never a suppression signal, because the caller decides open-PR routing (including whether `mint` is reached at all) before `mint` runs. `config.mint.bot_logins` is UNCHANGED and still read by the separate `/claude` PR-comment listener's own bot-login check (`comment_webhooks.rs`), which never called `mint::is_bot_loop` in the first place.

## Webhook listeners and run caps (CLAUDE-323, CLAUDE-364)

Each listener's daily run cap is its own DB-backed setting (CLAUDE-323): `config.webhook.max_runs_per_day` and `config.webhook_comment.max_runs_per_day`, default 20, validated `>= 1`, read from the live settings on each event rather than from `RunnerDefaults`. Two inbound webhook listeners, deliberately separate because their tokens differ in power: `POST /webhooks/forgejo/<source>` (`src/web/webhooks.rs`, CI-failure triage, a read-only `log_token_ref` plus a comment-only `write_token_ref`) and `POST /webhooks/forgejo-comment/<source>` (`src/web/comment_webhooks.rs`, `/claude` comment commands, a push-capable `write_token_ref`). The comment listener has TWO routes on one action, chosen by whether the thread is a pull request: a PR comment clones the head branch and pushes (CLAUDE-220), a plain-issue comment mints a `AI Agent = Queued` YouTrack issue for the `youtrack` action to work (CLAUDE-221) and clones nothing. The gate / trigger parsing / bot-login drop / dedupe key / caps are one implementation shared by both routes. They SHARE the signature verifier, the single replay-store instance, the rate-limiter type plus its builder, the repo allow-list matcher, and the run-accounting opener. Each surfaces as its own synthetic action (`webhook-triage`, `webhook-comment`) with its own Pause switch; both reserved names come from `crate::web::SYNTHETIC_ACTIONS`, the one predicate the daemon scan guard, the API, and the web layer all read. `config.webhook_comment.claude_timeout_seconds` (CLAUDE-364, default 600, validated `>= 1`) is the PR-comment route's own `claude` session timeout, read from the same live `webhook_comment` settings handle per command rather than the daemon-wide `RunnerDefaults::claude_timeout_seconds`, so a Settings save changes the ceiling for the next comment with no restart; the sibling CI-triage listener's `config.webhook.analysis_timeout_secs` is the equivalent knob for that listener's at-ingest classifier.
