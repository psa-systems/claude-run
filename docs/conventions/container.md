# Container runtime

The "builder-image note" referenced below is [Runtime images](governance.md#runtime-images-claude-37-claude-287-claude-94).

## Flat container layout (CLAUDE-253)

The container's layout is flat (CLAUDE-253): `/config`, `/data`, `/state`, plus a tmpfs `/run/claude-run`, instead of seven XDG paths under `/home/claudebot`. The image sets `CLAUDE_RUN_{CONFIG,DATA,STATE,RUNTIME}_DIR` plus `XDG_CONFIG_HOME=/config` (yt), `XDG_DATA_HOME=/data` (fj, which has no config-dir variable and which `provider/cli.rs`, `update.rs` and `secrets.rs` resolve through `dirs::data_dir()`), `CLAUDE_CONFIG_DIR=/config/claude-agent-home` and `GIT_CONFIG_GLOBAL=/config/git/config`, so each tool store is a subdirectory rather than a mount of its own and compose is three volumes rather than seven. `CLAUDE_CONFIG_DIR` names the SAME dir `agent_home` seeds, so an `exec`-run `claude auth login` lands where the agent reads rather than in a second config dir that authenticates nothing. `$HOME` is scratch. Outside the container (tests, local development) none is set and paths resolve through XDG, which the `config.rs` tests cover. One migration wrinkle: `job_outcomes.stream_log_path` is absolute, so rows written under the old layout point at paths that no longer exist; the log search resolves a missing recorded path against the current logs dir (the stream page already recomputed), so a moved deployment does not silently search nothing.

## Container identity (CLAUDE-247, CLAUDE-287, CLAUDE-310)

The container carries its own identity (CLAUDE-247). It bind-mounts NOTHING from the host: the operator runs `claude auth login`, `yt auth login`, `fj auth add-key` and `git config --global` INSIDE the container, and each login lands in its own subdirectory of the flat roots above (`claude-agent-home/`, `youtrack-cli/` and `git/` under `/config`, `forgejo-cli/` under `/data`), so the runner's credentials are separate from the operator's and the stack deploys where neither `$HOME` nor the invocation directory is reachable. Three pieces make that work. `src/agent_home.rs` treats a missing host login as a `warn` instead of aborting serve start (the old hard error crash-looped the container the operator needed to log into) and never removes a regular `.credentials.json`, because in the container that file IS the login rather than a link to the host's; the same guard covers `claude_config_dir` pointing at `$HOME/.claude`, where source and link are one path. `/usr/local/bin/gosu-entrypoint.sh` (CLAUDE-443), the shared, byte-identical entrypoint every first-party image installs per `governance/CONTAINER_UID_GID.md`, starts as root, runs the image's root hooks under `/etc/entrypoint.d/` (config seeding, then the data-dir chown that skips `workdirs`, a tree of job clones the runtime user made), chowns the rest of `DATA_DIRS`, and drops to `appuser` (uid/gid 1001) with `gosu` (installed from the upstream release binary and sha256-verified; Leap packages neither `su-exec` nor `gosu`). A compose `user:` pin disables the remap, hooks and chown and instead requires every `DATA_DIRS` entry to already be writable by that uid:gid; `docker compose exec` needs `--user appuser`. `catatonit`, not `gosu-entrypoint.sh`, is PID 1 (`ENTRYPOINT ["/usr/bin/catatonit", "--", "/usr/local/bin/gosu-entrypoint.sh", "/usr/local/bin/claude-run"]`, CLAUDE-310), so orphaned processes an agent session leaves behind when its own session exits are reaped instead of accumulating as zombies for the life of the container. CLAUDE-287 rebases the runtime stage onto `dev.a8n.run/pandoras-box/opensuse-dev` (the tag named in the builder-image note above), which already carries `yt`, `fj`, `nu`, `just` and `kingfisher` at the base tag's pinned versions, replacing the Alpine base's per-tool downloads (a PyPI `youtrack-cli` that was a DIFFERENT project from the org's `yt`, and a `cargo install forgejo-cli` that recompiled the crate every build, are both further in the past than that). The base also carries Docker, and `compose.yml`'s `claude-bot-docker` sidecar (Docker-in-Docker, `network_mode: service:claude-bot`, loopback-only `dockerd`) plus `DOCKER_HOST=tcp://127.0.0.1:2375` on `claude-bot` is what lets an agent session run `docker`, `docker compose` and `docker buildx`, closing the gap that made `just check` (which ends in `check-docker`) unable to run inside the container.

## BuildKit session healthcheck (CLAUDE-417)

A `docker buildx build` run from `claude-bot` against `claude-bot-docker` (`just check-docker`, and so `just check` / `just pre-push`) can die mid-build with the sidecar's `dockerd` logging:

```
level=warning msg="healthcheck failed" error="Unavailable: connection error: desc = \"transport: Error while dialing: only one connection allowed\"" timeout=15s
level=error   msg="healthcheck failed fatally" error="session healthcheck failed fatally: ..."
```

`strings /usr/bin/dockerd` on the `docker:29.6.2-dind` image this sidecar runs confirms both `healthcheck failed fatally` and `only one connection allowed` live in `dockerd` itself, clustered with `failed to hijack connection`, not in `docker`/`docker-buildx`: Docker 29.x folds BuildKit's session machinery directly into the daemon, which runs a `session.Manager` health monitor (5s interval, 2-strike failure threshold, matching the 5-second gap between the warning and the fatal line above) that re-dials the build session's gRPC health service on a second connection. `dockerd -H tcp://127.0.0.1:2375 --tls=false` (the sidecar's `command:` in `compose.yml`) proxies the whole build session through the single hijacked TCP connection the daemon accepted for that session ID, so the health monitor's second dial is rejected with exactly this error, and the second failed probe tears the session down. This is version-specific to the always-on BuildKit integration landing in Docker 29.x, reported upstream against the identical daemon line in [concourse/docker-image-resource#385](https://github.com/concourse/docker-image-resource/issues/385) ("dockerd crashes ~18s after startup... due to BuildKit healthcheck fatal failure (Docker 29.x)") and the older, narrower [moby/buildkit#748](https://github.com/moby/buildkit/issues/748). Neither TLS, the sidecar sharing `claude-bot`'s network namespace, nor client/daemon version skew is the cause: the concourse report reproduces the same failure over a Unix socket, and the health monitor's one-connection-per-session design is what fails regardless of transport encryption or namespace.

No setting in `compose.yml` or `oci-build/Dockerfile` removes this: it is inherent to BuildKit's session-health design in Docker 29.x whenever the session is proxied over a single hijacked connection, which is how every `docker buildx build` client talking to this daemon's classic (non-`docker-container`-driver) session router behaves. Retrying the build or silencing the log would hide a session teardown that can also corrupt the BuildKit layer cache for the next run (observed in this issue's reproduction: a `just check-docker` run interrupted mid-build left the next run unable to reuse cached dependency layers that normally survive), so neither is done here. A fix needs a BuildKit session transport that supports true multiplexed streams (e.g. buildx's own `docker-container` driver running a standalone `buildkitd`), which is a larger change than this sidecar's job (a `docker buildx build --target builder` run from inside the agent container) and is tracked separately rather than folded into this fix.

## CI images (CLAUDE-383)

`compose.yml` sets seven `RUNS_ON_*` environment variables on `claude-bot`, each the pullable image reference a CI workflow's `runs-on: ${{ vars.RUNS_ON_* }}` of the same name runs under, so an agent session can run the exact image CI runs (`docker run "$RUNS_ON_RUST_BUILDER_MUSL"`, or `image: ${RUNS_ON_RUST_BUILDER_MUSL}` in a compose file) instead of guessing a literal tag or reaching for an image from the GitHub Container Registry. The workflow-side name resolves to a runner LABEL, never an image; only the container-side environment variable is the image. `deploy/bot-CLAUDE.md`'s "CI images" section is what tells the agent this.
