# Container runtime

Full text of the `CLAUDE.md` conventions on this topic, moved there verbatim by CLAUDE-370. The index in `CLAUDE.md` links each heading below.

The "builder-image note" referenced below is [Runtime images](governance.md#runtime-images-claude-37-claude-287-claude-94).

## Flat container layout (CLAUDE-253)

The container's layout is flat (CLAUDE-253): `/config`, `/data`, `/state`, plus a tmpfs `/run/claude-run`, instead of seven XDG paths under `/home/claudebot`. The image sets `CLAUDE_RUN_{CONFIG,DATA,STATE,RUNTIME}_DIR` plus `XDG_CONFIG_HOME=/config` (yt), `XDG_DATA_HOME=/data` (fj, which has no config-dir variable and which `provider/cli.rs`, `update.rs` and `secrets.rs` resolve through `dirs::data_dir()`), `CLAUDE_CONFIG_DIR=/config/claude-agent-home` and `GIT_CONFIG_GLOBAL=/config/git/config`, so each tool store is a subdirectory rather than a mount of its own and compose is three volumes rather than seven. `CLAUDE_CONFIG_DIR` names the SAME dir `agent_home` seeds, so an `exec`-run `claude auth login` lands where the agent reads rather than in a second config dir that authenticates nothing. `$HOME` is scratch. A HOST install sets none of these and still resolves through XDG, which the `config.rs` tests cover. One migration wrinkle: `job_outcomes.stream_log_path` is absolute, so rows written under the old layout point at paths that no longer exist; the log search resolves a missing recorded path against the current logs dir (the stream page already recomputed), so a moved deployment does not silently search nothing.

## Container identity (CLAUDE-247, CLAUDE-287, CLAUDE-310)

The container carries its own identity (CLAUDE-247). It bind-mounts NOTHING from the host: the operator runs `claude auth login`, `yt auth login`, `fj auth add-key` and `git config --global` INSIDE the container, and each login lands in its own subdirectory of the flat roots above (`claude-agent-home/`, `youtrack-cli/` and `git/` under `/config`, `forgejo-cli/` under `/data`), so the runner's credentials are separate from the operator's and the stack deploys where neither `$HOME` nor the invocation directory is reachable. Three pieces make that work. `src/agent_home.rs` treats a missing host login as a `warn` instead of aborting serve start (the old hard error crash-looped the container the operator needed to log into) and never removes a regular `.credentials.json`, because in the container that file IS the login rather than a link to the host's; the same guard covers `claude_config_dir` pointing at `$HOME/.claude`, where source and link are one path. `oci-build/entrypoint.sh` starts as root, chowns the mounted volumes (skipping `workdirs`, a tree of job clones the runtime user made) and drops to `claudebot` with `setpriv --reuid=claudebot --regid=claudebot --init-groups` (CLAUDE-287; Leap packages neither `su-exec` nor `gosu`, and `setpriv`, already in the base, is the equivalent gosu's own README names), which is pattern 3 of `governance/CONTAINER_UID_GID.md` and a recorded exception to BUILD.md's non-root-start mandate; `user:` must therefore never be set in compose, and `docker compose exec` needs `--user claudebot`. `catatonit`, not `entrypoint.sh`, is PID 1 (`ENTRYPOINT ["/usr/bin/catatonit", "--", "/usr/local/bin/entrypoint.sh"]`, CLAUDE-310), so orphaned processes an agent session leaves behind when its own session exits are reaped instead of accumulating as zombies for the life of the container. CLAUDE-287 rebases the runtime stage onto `dev.a8n.run/pandoras-box/opensuse-dev` (the tag named in the builder-image note above), which already carries `yt`, `fj`, `nu`, `just` and `kingfisher` at the base tag's pinned versions, replacing the Alpine base's per-tool downloads (a PyPI `youtrack-cli` that was a DIFFERENT project from the org's `yt`, and a `cargo install forgejo-cli` that recompiled the crate every build, are both further in the past than that). The base also carries Docker, and `compose.yml`'s `claude-bot-docker` sidecar (Docker-in-Docker, `network_mode: service:claude-bot`, loopback-only `dockerd`) plus `DOCKER_HOST=tcp://127.0.0.1:2375` on `claude-bot` is what lets an agent session run `docker`, `docker compose` and `docker buildx`, closing the gap that made `just check` (which ends in `check-docker`) unable to run inside the container.

## CI images (CLAUDE-383)

`compose.yml` sets seven `RUNS_ON_*` environment variables on `claude-bot`, each the pullable image reference a CI workflow's `runs-on: ${{ vars.RUNS_ON_* }}` of the same name runs under, so an agent session can run the exact image CI runs (`docker run "$RUNS_ON_RUST_BUILDER_MUSL"`, or `image: ${RUNS_ON_RUST_BUILDER_MUSL}` in a compose file) instead of guessing a literal tag or reaching for an image from the GitHub Container Registry. The workflow-side name resolves to a runner LABEL, never an image; only the container-side environment variable is the image. `deploy/bot-CLAUDE.md`'s "CI images" section is what tells the agent this.
