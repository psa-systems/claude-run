# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# claude-run

YAML-driven runner for Claude Code: poll an external source (YouTrack issues, Forgejo PRs, ...), feed each job to `claude --print`, do something with the result. Shipped as a single Rust binary (`claude-run`) that doubles as a CLI and a long-running daemon with a unix-socket API.

## Shape

- Rust binary, library + bin. `clap` derive. Subcommand tree: `claude-run {run,serve,stop,restart,trigger,cancel,pause,resume,status,action,access,secret,migrate,import,version}`.
- Actions are YAML files under `$CLAUDE_RUN_CONFIG_DIR/actions/` (default `~/.config/claude-run/actions/`). Each action's `input.command` / `filter` / `pre[]` / `prompt` / `post[]` is a nu snippet shelled out via the host's `nu` binary.
- Runtime state in SQLite at `$CLAUDE_RUN_DATA_DIR/state.db` by default, or in PostgreSQL when the operator sets one (CLAUDE-250; see the `[database]` note below). Per-attempt stream logs at `$CLAUDE_RUN_STATE_DIR/logs/<action>/streams/<key>-attempt-<n>.jsonl`, bounded by the CLAUDE-245 sweep (see below).
- Daemon (`claude-run serve`) owns scheduling and exposes an HTTP API over `$CLAUDE_RUN_RUNTIME_DIR/daemon.sock`. CLI subcommands delegate to the daemon when reachable, else operate directly on the DB. The socket is the CLI's control plane and nothing else: `api::router` is built twice from one `api_state`, bare-path on the socket and nested under `/api` on the TCP listener, which is what the web UI's own buttons POST to. `serve --no-socket` skips the bind for a deployment with no CLI operator, and the container image runs that way (`CMD ["serve", "--no-socket"]`) because the socket has no auth gate (the CLAUDE-48 token wraps only the TCP router) and would otherwise sit in the same container as the agent, running as the same user. `trigger` and `cancel` then fail naming that reason instead of "no daemon"; the DB-direct subcommands are unaffected.
- Runtime tool dependencies (host-installed, not bundled in the binary): `nu`, `claude` (Claude Code CLI), `timeout` (coreutils). Optional: `yt`, `fj`, `git` if the actions need them.
- Forgejo home: `psa-systems/claude-run`.

## Commands

- `just check`: fmt + clippy + build + tests + builder-stage docker compile (the full CI gate). `just pre-commit` runs the checks inside the builder image via `docker run`.
- CI's exact steps (`.forgejo/workflows/check.yml`): `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo build --all-targets`, then `cargo test` twice: once on SQLite, once with `CLAUDE_RUN_TEST_DATABASE_URL=postgres://...` set, which switches every test fixture onto Postgres (one schema per test). A DB change must pass both.
- Single test: `cargo test <name_substring>` (e.g. `cargo test shipped_action_queries_are_disjoint`); one module: `cargo test native::youtrack::`. Unit tests live inline in `src/**` under `mod tests` on the library target; `tests/fixtures/` holds data only.
- `just run <args>` = `cargo run -- <args>` (debug build). `just build-static` builds the musl binary via Docker into `./dist/claude-run`.
- Any test that execs a stub script must create it with `testutil::write_stub`, never `fs::write` + `set_permissions` (ETXTBSY race across test threads, CLAUDE-224 / CLAUDE-255).

## Code map

- Entry: `src/bin/claude-run.rs` (clap) -> `client.rs` (talk to the daemon socket) or direct DB ops. `daemon.rs` hosts `serve`: `scheduler.rs` ticks, `Dispatcher::execute` runs an action via `run_action_inner`.
- Two action kinds (`ActionKind` in `action.rs`): `scripted` runs the generic nu pipeline in `job.rs` (`snippet.rs` execs `nu`, `claude.rs` execs `claude`); native kinds route through `native::handler_for` to a Rust handler in `src/native/` (`youtrack`, `closed_issue_summary`) that owns its whole run. Adding a native kind means a new `ActionKind` variant, a handler, a `handler_for` arm, and usually a structured editor in `web/native_forms.rs` + `templates/*_editor.html`.
- Native handlers reach YouTrack / Forgejo / GitHub only through the `provider` traits (`IssueTracker`, `Forge`); `provider/cli.rs` shells out to `yt` / `fj`, `provider/github.rs` covers GitHub, and `provider/audit.rs` wraps the tracker to cap and attribute a run's issue writes (CLAUDE-234). No raw REST in handlers.
- Web: `web/mod.rs` (axum + askama templates from `templates/`, compiled into the binary) mounts `api::router` under `/api` plus the two webhook listeners. `settings.rs` owns DB-backed runtime config; `config.rs` holds the serde schema and bootstrap file.
- DB: `db.rs` holds the pool and two embedded migrators, `migrations/sqlite/` and `migrations/postgres/`. Every schema change needs a matching migration in BOTH directories. Queries are runtime `sqlx::query` (no compile-time macros, no offline `.sqlx` data).
- Shipped actions in `actions/*.yml` are `include_str!`'d by tests in `action.rs`, so editing one can break a unit test.

## Conventions

- Governance lives at `niceguyit/governance`. `CHECKLIST.md`, `CI.md`, `PRE_COMMIT.md`, `FORGEJO_ORGS.md`, `GIT_WORKFLOW.md` are the source of truth; this file documents only claude-run-specific deviations.
- Builder image: `dev.a8n.run/pandoras-box/rust-builder-musl:v1.1.0-rust1.98.1-alpine`. The binary still ships as a Generic Package for host installs. There is also a runtime image (CLAUDE-37, rebased onto the org's dev image in CLAUDE-287): `oci-build/Dockerfile --target runtime` is `FROM dev.a8n.run/pandoras-box/opensuse-dev:v1.11-leap-16.0`, which already carries the pinned toolchain (`nu`, `claude`, `yt`, `fj`, `gh`, `just`, `kingfisher`, `timeout`, `git`, `docker`) at the versions the base tag names; moving a tool means bumping that tag, not editing a Dockerfile `RUN` block. CI publishes the built image to the Forgejo OCI registry as `dev.a8n.run/psa-systems/claude-run:{vX.Y.Z,latest}` with the same tag set as the binary, from its own workflow `.forgejo/workflows/build-image.yml` (split out of `build-binary.yml` in CLAUDE-94), and `compose.yml` runs the published image. The container user's `~/.claude/CLAUDE.md` is the slim bot file `deploy/bot-CLAUDE.md`, so the agent never inherits the operator's interactive global CLAUDE.md. See README "Containerized deployment".

- The web UI bootstraps itself: an exposed instance with no credential serves only `/setup`, which writes an argon2id admin hash to the `web_admin` table (`src/web_admin.rs`, migration `0020`) and is refused once one exists. `auth::resolve_gate` now returns a gate carrying whichever credentials exist (bearer token from `auth_token_ref`, DB administrator, or neither), and an unresolvable `auth_token_ref` is a `warn` with bearer auth disabled for the run rather than the old fail-closed that dropped the whole TCP listener. That old behaviour was unrecoverable in a container: the CLI that would store the secret is not the interface a container operator has. The gate holds the administrator behind an `Arc<RwLock<..>>` the setup handler swaps, so a first-run setup authenticates the next request with no restart. Sessions are HMAC'd with the admin's `session_key`, rotated on a password change, falling back to the token where no administrator exists. Where no administrator exists the pre-setup `auth_username` + token-plaintext login still works, so host installs are unchanged. The container image seeds `deploy/container-config.toml` (`bind = "0.0.0.0"`) into an empty config volume, because a loopback bind in a container is reachable from nothing outside it.

- Nothing runs without a Claude credential (`src/readiness.rs`). The scheduler tick, `Dispatcher::execute` and the trigger endpoint all consult `ReadinessGate` the way they consult `pause::PauseGate`, and the two states stay distinct: a pause is an operator decision, unready is an instance that was never finished. Ready means any of a `.credentials.json` in the agent config dir (on a host, the symlink to the operator's login), a stored API key, or `ANTHROPIC_API_KEY` in the env, so host installs are unaffected. The transition is logged once in each direction rather than per tick; the dashboard shows a banner and `/api/status` carries `ready` + `not_ready_reason`. This is what stopped a fresh container from querying YouTrack every tick and logging an auth error per action, on runs that could only have failed at the `claude` call and burned an attempt. CLAUDE-269 adds a second, independent not-ready axis on the same gate: `login_required`, an expired or revoked login the credential check alone cannot see because `.credentials.json` stays on disk. `ReadinessGate::trip_login_required` / `clear_login_required` are called from `ClaudeInvoker::invoke` (a structured `authentication_failed` on the stream, or three repeated `system`/`api_retry` events well before `claude_timeout_seconds`) and from a daemon status probe (`claude auth status --json`, `src/service_auth.rs::probe_claude_login`, run at startup, every 10 minutes while ready, every 60 seconds while login-required, skipped on `no_credential`); detection matches only the structured `error` field, never the CLI's human-readable wording. `pause::PauseGate::with_readiness` carries the gate into every `RunPause`, so the existing per-job checkpoints stop a run for this reason too, with no new call sites, closing with `exit::LOGIN_REQUIRED` (8) rather than `exit::PAUSED`. It clears with no restart on a completed brokered sign-in, an API-key save, or the probe reporting `loggedIn: true`.

- `claude auth login` is brokered from the Settings Auth card (`src/claude_login.rs`), so the container gets a real subscription login and not just an API key. The CLI's redirect is a paste-the-code callback, not a `localhost` listener, and over pipes it prints the authorize URL then reads the code from stdin: the broker spawns it under the agent config dir, hands the URL to the page, and writes the pasted code back. The child is held in daemon state between the two requests because it owns the PKCE verifier; a refused code returns the CLI's own wording and keeps the session (the CLI re-arms its prompt), cancel and a 15-minute expiry kill it, and the spawn plus the bounded read run through `blocking::in_place` per CLAUDE-228.

- The daemon holds its own service logins, entered in the web UI (Settings -> Auth, the card at the top of `/settings`). `src/service_auth.rs` materializes them where the CLIs actually look: a single-file `yt` config at `<config_dir>/auth/youtrack.yml` named by `YOUTRACK_CLI_CONFIG` (exported once at serve start, before any child, so a later save needs no restart and a per-job `token_ref` still wins by setting the same var in the child's own env), a `keys.json` in the daemon's XDG data dir through the same `secrets::write_fj_keys` the per-job path uses, a GitHub `hosts.yml` written by `gh auth login --with-token` itself under `<config_dir>/auth/gh` named by `GH_CONFIG_DIR` (CLAUDE-307; every `gh` child, including `GithubForge`'s own lazy `gh auth token --hostname <host>` fallback used when an action sets no `github.token_ref`, then reads that same login with no restart), and an `ANTHROPIC_API_KEY` handed to `ClaudeInvoker` through an `Arc<RwLock<Option<String>>>` the Settings save swaps. The `config.auth` document (section `Auth`) stores only URLs, the Forgejo host, the GitHub host, and the four fixed secret names; the tokens live encrypted in the secrets store. That store needs no pre-provisioned key and the runner owns it: `secrets::ensure_key` (serve start, and the CLI before it writes) puts it at `<config_dir>/secrets.key`, 0600. Config, not data, because the ciphertext is `state.db` in the data dir and a key beside its ciphertext defeats the point of encrypting the store; a key still at the old `<data_dir>/secrets.key` is MOVED on the next start. Generation happens only while the store is empty: a missing key with secrets already stored is a hard error naming them, never a silent replacement that would orphan them. `SecretsKey::load` is now a plain read with one behaviour. The key is extracted from wherever it sits on a line, so a SOPS-decrypted `data: AGE-SECRET-KEY-...` or an env-style file works as a key file, and a group- or world-readable key file loads with a `warn` rather than failing (an operator's delivery may be 0644 deliberately). This is what fixes the container's `no instance configured. Run 'yt auth login'` on every poll: the daemon's own provider calls had nothing but host auth, and a container has no host operator.

- Every `git` subprocess authenticates from the forge key store and reports why it failed (CLAUDE-252). `provider::shallow_clone` is the one clone path for all three actions, and `provider::git_error` builds every git failure as the exit code PLUS the tail of git's own stderr, redacted through `forge_log::redact` with the URL's userinfo passed as a known secret (the reason string reaches `run_events` and can reach a YouTrack comment, and the clone URL carries a token). Before it, `git clone exited 128` and `git push exited 1` were the entire diagnosis for a missing credential, an unknown host, a deleted branch, a rejected non-fast-forward and a protected branch alike. The `youtrack` action was also the only one cloning the UNauthenticated URL from the YouTrack VCS integration ("host git identity handles auth"), which is exactly what a container does not have, so every job failed at the pre step; it now resolves through `Forge::clone_url` like the other two, stripping the scheme from `repo_host` because that lookup wants a bare host, and falls back to the plain URL with a `warn` so a host install using a credential helper is unchanged. `{{clone_url}}` in the prompt stays unauthenticated: the agent must never be handed the token.

- The container's layout is flat (CLAUDE-253): `/config`, `/data`, `/state`, plus a tmpfs `/run/claude-run`, instead of seven XDG paths under `/home/claudebot`. The image sets `CLAUDE_RUN_{CONFIG,DATA,STATE,RUNTIME}_DIR` plus `XDG_CONFIG_HOME=/config` (yt), `XDG_DATA_HOME=/data` (fj, which has no config-dir variable and which `provider/cli.rs`, `update.rs` and `secrets.rs` resolve through `dirs::data_dir()`), `CLAUDE_CONFIG_DIR=/config/claude-agent-home` and `GIT_CONFIG_GLOBAL=/config/git/config`, so each tool store is a subdirectory rather than a mount of its own and compose is three volumes rather than seven. `CLAUDE_CONFIG_DIR` names the SAME dir `agent_home` seeds, so an `exec`-run `claude auth login` lands where the agent reads rather than in a second config dir that authenticates nothing. `$HOME` is scratch. A HOST install sets none of these and still resolves through XDG, which the `config.rs` tests cover. One migration wrinkle: `job_outcomes.stream_log_path` is absolute, so rows written under the old layout point at paths that no longer exist; the log search resolves a missing recorded path against the current logs dir (the stream page already recomputed), so a moved deployment does not silently search nothing.

- The container carries its own identity (CLAUDE-247). It bind-mounts NOTHING from the host: the operator runs `claude auth login`, `yt auth login`, `fj auth add-key` and `git config --global` INSIDE the container, and each login lands in its own subdirectory of the flat roots above (`claude-agent-home/`, `youtrack-cli/` and `git/` under `/config`, `forgejo-cli/` under `/data`), so the runner's credentials are separate from the operator's and the stack deploys where neither `$HOME` nor the invocation directory is reachable. Three pieces make that work. `src/agent_home.rs` treats a missing host login as a `warn` instead of aborting serve start (the old hard error crash-looped the container the operator needed to log into) and never removes a regular `.credentials.json`, because in the container that file IS the login rather than a link to the host's; the same guard covers `claude_config_dir` pointing at `$HOME/.claude`, where source and link are one path. `oci-build/entrypoint.sh` starts as root, chowns the mounted volumes (skipping `workdirs`, a tree of job clones the runtime user made) and drops to `claudebot` with `setpriv --reuid=claudebot --regid=claudebot --init-groups` (CLAUDE-287; Leap packages neither `su-exec` nor `gosu`, and `setpriv`, already in the base, is the equivalent gosu's own README names), which is pattern 3 of `governance/CONTAINER_UID_GID.md` and a recorded exception to BUILD.md's non-root-start mandate; `user:` must therefore never be set in compose, and `docker compose exec` needs `--user claudebot`. `catatonit`, not `entrypoint.sh`, is PID 1 (`ENTRYPOINT ["/usr/bin/catatonit", "--", "/usr/local/bin/entrypoint.sh"]`, CLAUDE-310), so orphaned processes an agent session leaves behind when its own session exits are reaped instead of accumulating as zombies for the life of the container. CLAUDE-287 rebases the runtime stage onto `dev.a8n.run/pandoras-box/opensuse-dev` (the tag named in the builder-image note above), which already carries `yt`, `fj`, `nu`, `just` and `kingfisher` at the base tag's pinned versions, replacing the Alpine base's per-tool downloads (a PyPI `youtrack-cli` that was a DIFFERENT project from the org's `yt`, and a `cargo install forgejo-cli` that recompiled the crate every build, are both further in the past than that). The base also carries Docker, and `compose.yml`'s `claude-bot-docker` sidecar (Docker-in-Docker, `network_mode: service:claude-bot`, loopback-only `dockerd`) plus `DOCKER_HOST=tcp://127.0.0.1:2375` on `claude-bot` is what lets an agent session run `docker`, `docker compose` and `docker buildx`, closing the gap that made `just check` (which ends in `check-docker`) unable to run inside the container.
- The governance template's `.env.example`, HOST_IP/PORT split, and fixed per-service port assignments do NOT apply. The daemon binds a unix socket by default (not in the container image, which runs `serve --no-socket`); the TCP web UI is reachable on `127.0.0.1:7321` by default (`WebConfig`, `src/config.rs`). The container runtime ships its own `compose.yml` (CLAUDE-37; see the builder-image note above).
- Action schema is documented in `actions/SCHEMA.md`. Authoritative; changes here ripple to both the runner and the doc.
- Not every action works code. `closed-issue-summary.yml` (`kind: closed-issue-summary`, `src/native/closed_issue_summary.rs`, CLAUDE-218) is the runner used as a REPORTING tool: it counts and lists the issues closed in a rolling window across a project list, files that report as a new issue, and links it to a nominated parent as a subtask. It clones no repository, starts no agent session, and opens no pull request. It is partitioned off `youtrack.yml` on the `AI Agent` axis (the worker pins `Queued`; a reporting `query` must pin its own value), the same "one action, one job" split CLAUDE-215 made for audits on the project and tag axes (`audit-run.yml` selects `project: AUDIT tag: Audit-*`, `youtrack.yml` its complement `(project: -AUDIT or tag: -Audit-*)`). `shipped_action_queries_are_disjoint` in `src/action.rs` guards the partition; `youtrack.yml` deliberately writes no negation, because YouTrack 400s a query naming an `AI Agent` value that is not in the bundle.
- The state store is SQLite or PostgreSQL, chosen by the operator (CLAUDE-250). `src/db.rs` opens ONE `sqlx::AnyPool` (`db::DbPool`) for either, so no module outside it names a backend type, and it holds the two migration sets: `migrations/sqlite/` is the original twenty files, byte-identical so a deployed `state.db` matches its recorded checksums and re-runs nothing, and `migrations/postgres/0001_init.sql` is a hand-written squash of their end state (`BIGINT` for every integer, `DOUBLE PRECISION` for `REAL`, `BYTEA` for `BLOB`, `GENERATED BY DEFAULT AS IDENTITY` for the autoincrement keys, boolean-ish columns left as integer 0/1). `Any` forwards SQL unchanged, so `db::q` is the chokepoint every statement passes through: it renumbers `?` / `?N` into `$n` for Postgres and expands the two dialect-neutral functions the call sites are written in, `strpos(haystack, needle)` and `elapsed_seconds(from, to)`. Everything else is spelled portably in place (`COALESCE`, `ON CONFLICT DO NOTHING`, `CAST(... AS BIGINT)` around a `SUM()` over an integer, `<table>.<col>` on the right of a `DO UPDATE SET`, no negative `LIMIT`), and integer 0/1 columns decode through `db::flag` because `Any` will not coerce an integer to a `bool`. Selection is a bootstrap key, not a DB-backed setting: `[database] url`, overridden by `CLAUDE_RUN_DATABASE_URL`, overridden by the contents of the file named by `CLAUDE_RUN_DATABASE_URL_FILE`. Unset is SQLite; an unknown scheme or an unreachable server stops the daemon rather than falling back. `compose.yml` carries `claude-bot-postgres` behind a `postgres` profile. Setting `CLAUDE_RUN_TEST_DATABASE_URL` re-runs the WHOLE test suite against Postgres (one schema per fixture pool), which is what CI does after the SQLite pass. See README "State store backend". A schema change is a new incremental file in EACH migration directory (e.g. `migrations/sqlite/0021_ci_failures.sql` plus `migrations/postgres/0002_ci_failures.sql` for the CLAUDE-272 CI-failure store), with the same end schema on both sides; the twenty original SQLite files, and any shipped since, stay byte-identical.

- CLAUDE-272 added the CI-failure store: `ci_failures` (one row per distinct failure, keyed on `(repo, workflow_id, job_name)`, nullable `issue_key` because a failure seen only on a human's PR has no issue), `ci_failure_tests` (its failing-test fingerprint, unique per `(failure_id, test_id)`), `ci_failure_runs` (one row per sighting: commit, branch, PR number, timestamp), and `agent_pull_requests` (every PR the runner's own `youtrack` action opens, unique per `(host, repo, pr_number)`, carrying `fix_attempts` so a re-queued issue is recognised as a continuation). The new module `src/ci_failure/` holds `fingerprint::{failing_tests, fingerprint}` (pure string parsing of cargo test output, no LLM, no I/O, modelled on `src/infra_failure.rs`; falls back to `mint::failure_signature` when nothing cargo-shaped parses) and `store` (the async functions over `DbPool`, notably `find_match`, which answers "which issue does this failure belong to" by test-id overlap within the same repo/workflow/job, preferring `open` over `resolved` over `pr_only` and the newest on a tie). `ci_failure_runs` joins `RETENTION_TABLES` (`src/retention.rs`) since it is per-sighting history; the other three tables are never pruned, because a resolved failure or a merged PR must still match a regression months later. `agent_pull_requests` is wired into the `youtrack` action by CLAUDE-275 (below); CLAUDE-273 (below) wires `ci_failures` / `ci_failure_tests` / `ci_failure_runs` into the webhook.
- CLAUDE-275 wires the `agent_pull_requests` store into the `youtrack` action so a re-queued issue continues its own open PR's branch instead of opening a second one. `PullRequest` (`src/provider/mod.rs`) gained `head_branch: Option<String>`, filled in by `CliBackend::create_pr`'s branch strategy and by `GithubForge::create_pr` (both always branch-backed) with the branch just pushed; the AGit strategy leaves it `None`, since `refs/for/<base>` produces no server branch. `process_job` (`src/native/youtrack.rs`) looks up `store::agent_pr_for_issue` before `pre`: an `open` record is confirmed live against `Forge::list_open_prs`, and when still open its `head_branch` is what `run_pre` clones instead of the default branch, with `{{existing_pr_url}}` / `{{existing_branch}}` (new prompt placeholders, empty on a fresh pickup) telling the agent to fix that same branch rather than open another. A record absent from the open list is marked `closed` (merged and closed are not distinguishable from an open-PR listing alone) and pickup falls back to the default branch as before; the AGit strategy always skips resume (logged at `info`), since it has nothing to resume onto. `finalize` cannot make the store's async write itself - it is a synchronous state machine whose own unit tests run with no tokio runtime - so `Finalized::CodeReview` carries `pr_number` / `head_branch` out and `process_job` calls `store::record_agent_pr` right after `finalize` returns, but ONLY on a non-resumed success: re-recording a resumed PR would collide with the store's `UNIQUE(host, repo, pr_number)`. A failed record write logs at `error`, reaches `run_events` through a new `Forge::note` default-no-op method (`CliBackend` pushes it onto the same notice queue `take_notices` already drains), and gets a follow-up issue comment naming it, none of which fail the job: the PR already exists and the issue already sits at Code Review. `run_pre`'s resume clone pins that `head_branch` into `provider::shallow_clone`, and CLAUDE-311 makes that pinned clone also fetch the remote's default branch and set `origin/HEAD`, because `CliBackend::resolve_feature_branch`'s base-branch resolution depends on it.
- CLAUDE-273 moves CI-failure dedupe off a `yt` full-text search and onto the CLAUDE-272 store's failing-test overlap, and makes it unconditional: `mint::mint` (`src/mint.rs`) no longer searches YouTrack at all and never declines for a duplicate or a resolved issue - `SkippedResolved`, `SkippedDuplicateOpen`, `AssociatedWithOpen`, and `SkippedAutoFixDisabled` are gone from `MintOutcome`, and `mint` only creates once the bucket/cap gates above it pass (CLAUDE-276 later removes the open-PR and bot-loop gates from `mint` itself). The webhook consumer (`triage_and_mint` in `src/web/webhooks.rs`) fingerprints the redacted log (`ci_failure::fingerprint::fingerprint`) BEFORE triage and calls `store::find_match` against it: an `open` match calls `attach_run` / `add_tests` and comments the run + failing tests onto the existing issue with no triage and no `claude` call at all (`attach_to_open_failure`); a `resolved` match is a regression - `reopen_resolved_failure` reopens with `set_state(mint.target_state)`, posts a "Regression: ..." comment, flips the store row back to `open`, and only then runs triage so the analysis lands as a follow-up comment and `AI Agent` is set exactly as a freshly minted issue of that bucket would be (`mint::queues_for_fix`, a `pub(crate)` wrapper around the same routing table `mint::mint` uses, so the two never disagree). No match (or a `pr_only` match with no open PR on the failing commit - CLAUDE-276 routes a `pr_only` match WITH an open PR separately, before `find_match` even runs) falls through to `classify_and_mint`, which is the pre-existing triage + mint pipeline preceded by ONE legacy-adoption lookup (`decide_with_legacy_adoption`, still a plain YouTrack `#Unresolved` search on `mint::legacy_collapse_key` - the same root-cause/infra marker `mint` used to search, now `pub(crate)` and computed from plain arguments instead of a `MintRequest` it does not have yet) for an issue minted before the store existed; a `Created` outcome, or a legacy hit, is then recorded into the store (`record_new_store_row`) so the next sighting matches by test overlap rather than searching YouTrack again. A store read or write error is logged at `error` and fails the run (`ok = false`) rather than falling through to a mint, which would recreate the exact duplicate this issue removes. The webhook `auto_fix` toggle (`config.webhook.auto_fix`, CLAUDE-153) changes meaning to match: it no longer decides whether an issue is minted, only whether a `code_fix` / `auto_fix` issue's `AI Agent` gets set, so `No orphan notes` holds even with it off. The `Dedupe-Key:` / `Root-Cause-Key:` / `Branch:` / `Job:` body markers `mint::build_description` writes are UNCHANGED, because the legacy-adoption lookup above still reads it; only the searching stops. - CLAUDE-274 collapses the webhook's two `claude` passes (a tool-less classifier at ingest, a separate scheduled deep analysis later) into one: `src/triage::AnalysisClassifier` runs `Read,Grep,Bash` over the COMPLETE redacted log plus the failing workflow YAML, in a per-event `webhook-logs/analysis/<owner>_<repo>-run<N>/` directory it creates and removes itself, on a timeout from the new `config.webhook.analysis_timeout_secs` (default 600). Each run emits one `run usage` line and appends one NDJSON record to `logs/usage.jsonl`. Cost of record is the CLI's own `total_cost_usd`, never a hard-coded price table, so a price change needs no runner release.
- Every `claude` invocation records its own Claude plan (subscription) rate-limit reading, separate from the dollar spend above (CLAUDE-315). `usage::parse_stream_usage` also replays a stream log's `rate_limit_event` (a `status` plus a `five_hour` / `seven_day` window utilization, kept as the LAST one seen so a session's own retries do not average out) and every `api_retry` event (counted per reason into a `BTreeMap`); every field stays an `Option` and is never defaulted to `0` or `"unknown"`, because an old CLI or a session that made no API call reporting one leaves genuinely no data rather than a zero. `ClaudeInvoker::invoke` logs one `claude usage` line per invocation, at `warn` instead of `info` when the status is not `allowed` or either window's utilization is at least 0.9, and states `rate_limit = "absent"` explicitly when there was no event at all. `usage::record_invocation` then persists one row to the `claude_invocations` table (`migrations/{sqlite,postgres}/00{22,3}_claude_invocations.sql`) at every call site that invokes `claude` in `src/` (`job.rs`, `native/youtrack.rs`, `triage.rs`, `web/comment_webhooks.rs`), immediately after `invoke` returns and before any branch can drop the result; a write failure logs at `error` and never fails the job, because the invocation itself already succeeded or failed on its own terms. `src/state.rs`'s `every_claude_invoke_call_site_pairs_with_a_record_invocation_call` is a source-scan test (modeled on the CLAUDE-228 run-guard pairing test) that fails if a new `.invoke(` call site is added with no matching `record_invocation(` call beside it. The table joins `RETENTION_TABLES` (per-occurrence history, not a lookup table) and `import::TABLES` / `IDENTITY_COLUMNS` (so switching backends carries it over). `/reports` renders it as the "Claude plan usage" section: `report::claude_usage` queries the window, `web::build_usage_chart` turns it into an inline-SVG two-series line chart (five-hour and seven-day utilization, 0-100%) that breaks into a new polyline segment at each invocation with no rate-limit data at all rather than interpolating a fabricated reading, and flags a timed-out or failed invocation's marker in red; the section states the gap count explicitly and shows an empty-state message when the window holds no invocations, plus a table of the 20 most recent.
- Context is bounded per invocation, which is what makes spend linear in tool calls (DEV-706). `claude.autocompact` resolves action -> `config.claude.autocompact` -> `claude::DEFAULT_AUTOCOMPACT` (200000), and unlike `model` / `effort` the last step is a VALUE rather than no flag: the CLI's own `auto` scales the window to the model's whole context, so on a 1M-context model a long tool-heavy session never compacts, resends every completed operation's tool payloads on every turn, and cumulative spend grows with the SQUARE of the number of tool calls with tool output rather than reasoning dominating the bill. `StreamUsage::context_per_tool_call` (in the per-run record) is the measurement: flat as N grows is linear, rising with N is quadratic. `usage.rs`'s `context_per_tool_call_separates_quadratic_growth_from_linear` pins both shapes.

- The stream-log relay reports its own I/O failures instead of truncating in silence (CLAUDE-233). `relay_stamped_stdout` (`src/claude.rs`) is the only writer of `logs/<action>/streams/<key>-attempt-<n>.jsonl`, and it used to `break` on a write error with the error discarded. When the log partition filled, it stopped mid-line, claude kept running and exited 0, `parse_final_result` found no `result`, and the run was failed non-transiently as "claude stream did not end with a result event" - blaming the agent for a silence the runner produced, and burning an attempt against `max_attempts_per_key`. The relay now returns `io::Result`, `invoke` carries the reason out of the wait block, and a relay that died before the terminal `result` yields a `transient` failure naming the write error and the log path (`relay_failure_result`), so no attempt is spent; when the `result` was already captured the run still finalizes from it and the truncation logs at `warn`. The forensic signature of the old bug in an existing log is a file ending mid-line at an exact multiple of 4096, the page boundary where the kernel's short write stopped.

- The READ side of that same file carries its `io::Error` out too, instead of collapsing it (CLAUDE-256). `parse_final_result`, `last_assistant_text` and `read_tail` (`src/claude.rs`) all return `io::Result` rather than swallowing a read failure into `None` or an empty string. A stream log the runner cannot read finalizes as `read_failure_result`, `transient`, so it spends no attempt and is picked up again on the next poll; a log that reads fine but simply never got a `result` event keeps its existing non-transient "claude stream did not end with a result event" wording, because that is a real claude-side outcome rather than a runner fault. `read_tail`, the last-resort fallback in `friendly_failure_summary`, also advances its cut point forward to the nearest UTF-8 character boundary before slicing (CLAUDE-263): the fixed byte offset it used to slice at can land inside a multi-byte character in agent output, which panicked rather than returning a tail up to three bytes short of the cap.

- No `claude` child can leave work running past its own turn (CLAUDE-280). `ClaudeInvoker::invoke` (`src/claude.rs`) sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` in every child's environment and passes `--disallowedTools=Monitor,ScheduleWakeup` unconditionally, for every caller (the native runners, the triage classifier, the comment webhook, and scripted jobs): a session run under `--print` is over the instant its turn ends, so a turn that ends "waiting" for a `Bash` background task, a `Monitor`, or a `ScheduleWakeup` never resumes, and run 10822 (CLAUDE-269) is what happened without this - a session that reported success while `cargo test --lib` was still running in the background. `wait_or_cancel` already terminates a leftover background task that outlives the terminal `result`, and that termination is the backstop this issue adds: `killed_tasks_after_result` (`src/claude.rs`) scans the stream log for a `system`/`task_updated` event with `patch.status: killed` AFTER the terminal `result`, and a match overrides what would otherwise be a captured success into a non-transient failure naming the task id. `parse_final_result` still selects the `result` event by type rather than by line position (CLAUDE-107), so a clean run with ordinary trailing `system` events is unaffected; only a *killed* one flips the outcome.

- `logs/` is bounded by its own sweep (CLAUDE-245). Nothing deleted stream logs before it: `crate::gc::sweep` walks `workdirs/*/*` and `crate::retention::sweep` prunes DB tables, and neither looked at `logs/`, so the directory only ever grew (2473 files / 2.8 GB on host-a, oldest five months back). That is the root cause of CLAUDE-233 rather than a separate bug: the full log partition is what made the relay's write fail. `crate::gc::sweep_stream_logs` is the second sweep in the same module, deleting `logs/<action>/streams/*.jsonl` past `config.stream_log_gc.retention_days` (default 30) and logging its deleted / kept / bytes-reclaimed tally every pass at `info`. `daemon::stream_log_gc_loop` schedules it beside the other two on the `GC_TICK_SECS` cadence, first tick at serve start, reading the live handle so a Settings save applies next pass. What keeps an in-flight run's log is `daemon::inflight_stream_log_jobs`: the `(action, job_key)` pairs from `run_inflight_jobs` joined to runs with `ended_at IS NULL`, kept regardless of age, because a long `claude_timeout_seconds` job can outlive any window while its log is still being written. A failed read of that set skips the pass rather than sweeping with an empty set, since the wrong guess deletes a live run's only transcript.

- The other three writers under `logs/` are bounded by SIZE on that same tick (CLAUDE-257, CLAUDE-268). `logs/daemon.log` (opened `create+append` by `detach_now` and handed to daemonize as both stdout and stderr) and `logs/<action>/<output.file>` (`job::append_output_record`, opt-in per action) are single files appended to for the life of the install, so an age window never fires on either: `crate::gc::sweep_oversized_logs` copies a file past its ceiling to one predecessor (`<name>.1`, skipped by the walk so it is never rotated again) and truncates the original IN PLACE back to its newest half at a line boundary. In place because the daemon holds `daemon.log` open in append mode; a rename would leave it writing into the predecessor while the live log stayed empty. `logs/usage.jsonl` (DEV-707's per-run token and cost record, `usage::append_record`) is the third: it sits directly under `logs/`, so the action-directory walk never reaches it and it is bounded explicitly beside `daemon.log`, and because it is newline-delimited JSON the existing line-boundary cut is what keeps the survivor parseable instead of starting mid-record (CLAUDE-268). The ceilings extend `config.stream_log_gc` (`daemon_log_max_bytes` / `output_file_max_bytes`, 50 MiB each, `usage_log_max_bytes`, 8 MiB because a usage record is far shorter than a log line, `0` = unbounded) rather than adding a fourth loop, and the settings key keeps its `stream_log_gc` name because renaming the document's primary key would silently reset an operator's configured window. The `output.file` sink is bounded by size and never age-swept on purpose: it is an operator-configured data sink, and deleting it destroys the record it exists to keep. The `$CLAUDE_RUN_STATE_DIR` tree in `actions/SCHEMA.md` had described the removed nu runner (a `PAUSED` file, `state/<name>.json`, a dated `.log`) until CLAUDE-257 replaced it with the paths that exist.

- The last two trees under the state dir are bounded the same way, by AGE, on the same tick (CLAUDE-262). `snippets/<action>/<job_key>/` (`crate::snippet::snippet_dir_for`) is written once per scripted step (`filter` / `pre` / `prompt` / `post`) of every job and nothing ever removed it; `crate::gc::sweep_snippets` deletes a directory past `config.stream_log_gc.snippet_retention_days`, reusing the exact `run_inflight_jobs`-derived in-flight set `sweep_stream_logs` reads so a still-running job's own snippet directory is never deleted underneath it, and a failed in-flight read skips both sweeps for the same reason it skips the stream-log one. `webhook-logs/` (`crate::forge_log::write_artifact`, one redacted concatenated log per triaged CI run) is bounded the same way by `crate::gc::sweep_webhook_logs` against `config.stream_log_gc.webhook_log_retention_days`, but age-only with no in-flight guard: a webhook run is not a scheduled job and never appears in `run_inflight_jobs`. That sweep walks only the FILES directly under `webhook-logs/`, never its subdirectories, because `webhook-logs/analysis/<owner>_<repo>-run<N>/` (CLAUDE-274, replacing the old shared `webhook-logs/triage/`) is a PER-EVENT working directory the at-ingest `AnalysisClassifier` creates and removes itself once its session returns, not a per-run artifact the GC sweep needs to bound. Both new windows ride the existing `config.stream_log_gc` document rather than a fifth section, per the same "the settings key is the document's primary key" reasoning CLAUDE-257 used to keep that section's name unchanged.

- Each listener's daily run cap is its own DB-backed setting (CLAUDE-323): `config.webhook.max_runs_per_day` and `config.webhook_comment.max_runs_per_day`, default 20, validated `>= 1`, read from the live settings on each event rather than from `RunnerDefaults`. Two inbound webhook listeners, deliberately separate because their tokens differ in power: `POST /webhooks/forgejo/<source>` (`src/web/webhooks.rs`, CI-failure triage, a read-only `log_token_ref` plus a comment-only `write_token_ref`) and `POST /webhooks/forgejo-comment/<source>` (`src/web/comment_webhooks.rs`, `/claude` comment commands, a push-capable `write_token_ref`). The comment listener has TWO routes on one action, chosen by whether the thread is a pull request: a PR comment clones the head branch and pushes (CLAUDE-220), a plain-issue comment mints a `AI Agent = Queued` YouTrack issue for the `youtrack` action to work (CLAUDE-221) and clones nothing. The gate / trigger parsing / bot-login drop / dedupe key / caps are one implementation shared by both routes. They SHARE the signature verifier, the single replay-store instance, the rate-limiter type plus its builder, the repo allow-list matcher, and the run-accounting opener. Each surfaces as its own synthetic action (`webhook-forgejo`, `webhook-forgejo-comment`) with its own Pause switch; both reserved names come from `crate::web::SYNTHETIC_ACTIONS`, the one predicate the daemon scan guard, the API, and the web layer all read.

## Phases

The Rust port is complete: all six phases below are merged. This table is the historical record of that rollout, kept because code comments across the tree still cite these phase numbers.

| Phase | Scope                                                                | Status                          |
|-------|----------------------------------------------------------------------|---------------------------------|
| 1     | `run` / `migrate`, all core modules, SQLite-backed state             | merged                          |
| 2     | `serve [--detach]`, scheduler, unix-socket API, lock, pause-in-DB    | merged                          |
| 3     | Web UI (axum templates + HTMX + SSE), TCP listener, log streaming    | merged                          |
| 4     | Action edit / import / export through the API                        | merged (CLAUDE-7)               |
| 5     | Token auth for non-loopback binds                                    | merged (CLAUDE-48)              |
| 6     | Retention policy enforcement on the unbounded history tables, polish | merged (CLAUDE-172, CLAUDE-175) |

Two unrelated numbering schemes both say "Phase N", and a bare `grep 'Phase 3'` returns hits from both. The roadmap phases in this table are one (e.g. `src/web/mod.rs` "Phase 3" = Web UI, `src/auth.rs` "Phase 5" = token auth). The separate native-actions epic (CLAUDE-30..CLAUDE-34, tracked under CLAUDE-25) is the other; its comments carry the "native-action" qualifier (e.g. `src/native/youtrack.rs` "Phase 3 of the native-action epic" = CLAUDE-32, which is NOT roadmap Phase 3). Tell them apart by that qualifier and the CLAUDE-30..34 / CLAUDE-25 issue range; a bare "Phase N" with no "native-action" wording refers to this table.

Cross-cutting (not a numbered phase): a container runtime (CLAUDE-37, made self-contained in CLAUDE-247) runs the daemon and its spawned `claude` children in an isolated `$HOME` with a slim bot CLAUDE.md and its own logins, decoupled from the host's operator config. See `oci-build/Dockerfile` (`runtime` target), `oci-build/entrypoint.sh`, `compose.yml`, and `deploy/bot-CLAUDE.md`.

## Working on this repo

- Branch off `main` per `governance/GIT_WORKFLOW.md`. Run `just pre-commit` (or rely on the installed hook) before pushing.
- `just check` runs the same fmt + clippy + build + tests CI runs.
- The task runner is the shared `psa-systems/common` recipe set, vendored as the `common` submodule (`git submodule update --init` after a fresh clone). `justfile` configures it through variables (`pre_commit_mode := "docker"` + `dev_image` because there is no `compose.dev.yml`, `test_args := ""` so the library-target unit tests are not skipped) and overrides only `default`, `check`, and `run`. Prefer setting a common variable over shadowing a shared recipe. `default` is redefined locally (as the file's first recipe) because just resolves the default recipe by source order and a top-level definition outranks the imported one, so without it a bare `just` runs whichever local recipe comes first instead of common's `just --list` (CLAUDE-201). CI keeps its own `.forgejo/workflows/check.yml` rather than calling common's reusable one, which hardcodes `cargo test --bins`; making that configurable is tracked in #PC-6. It also deviates from governance `CI.md` ("Check runs on every push / PR"): the workflow still runs on every push and PR to `main`, but its compile job is skipped (via a leading `changes` job and an `if:`, not a workflow-level `paths-ignore`) when only `docs/**`, `README.md`, or `CLAUDE.md` changed (CLAUDE-286).
- Daemon smoke-test pattern: `CLAUDE_RUN_*_DIR=/tmp/...` env vars + a stub `claude` on `PATH` (see `src/bin/claude-run.rs` smoke tests for the shape).
- The legacy `scripts/claude-run.nu` is gone as of the governance-conformance PR. The Rust binary is the only runner.
