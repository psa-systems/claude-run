# claude-run

YAML-driven runner for Claude Code: poll an external source (YouTrack issues, Forgejo PRs, ...), feed each job to `claude --print`, do something with the result. Shipped as a single Rust binary (`claude-run`) that doubles as a CLI and a long-running daemon with a unix-socket API.

## Shape

- Rust binary, library + bin. `clap` derive. Subcommand tree: `claude-run {run,serve,stop,restart,trigger,pause,resume,status,action,migrate,import,version}`.
- Actions are YAML files under `$CLAUDE_RUN_CONFIG_DIR/actions/` (default `~/.config/claude-run/actions/`). Each action's `input.command` / `filter` / `pre[]` / `prompt` / `post[]` is a nu snippet shelled out via the host's `nu` binary.
- Runtime state in SQLite at `$CLAUDE_RUN_DATA_DIR/state.db` by default, or in PostgreSQL when the operator sets one (CLAUDE-250; see the `[database]` note below). Per-attempt stream logs at `$CLAUDE_RUN_STATE_DIR/logs/<action>/streams/<key>-attempt-<n>.jsonl`, bounded by the CLAUDE-245 sweep (see below).
- Daemon (`claude-run serve`) owns scheduling and exposes an HTTP API over `$CLAUDE_RUN_RUNTIME_DIR/daemon.sock`. CLI subcommands delegate to the daemon when reachable, else operate directly on the DB. The socket is the CLI's control plane and nothing else: `api::router` is built twice from one `api_state`, bare-path on the socket and nested under `/api` on the TCP listener, which is what the web UI's own buttons POST to. `serve --no-socket` skips the bind for a deployment with no CLI operator, and the container image runs that way (`CMD ["serve", "--no-socket"]`) because the socket has no auth gate (the CLAUDE-48 token wraps only the TCP router) and would otherwise sit in the same container as the agent, running as the same user. `trigger` and `cancel` then fail naming that reason instead of "no daemon"; the DB-direct subcommands are unaffected.
- Runtime tool dependencies (host-installed, not bundled in the binary): `nu`, `claude` (Claude Code CLI), `timeout` (coreutils). Optional: `yt`, `fj`, `git` if the actions need them.
- Forgejo home: `psa-systems/claude-run`.

## Conventions

- Governance lives at `niceguyit/governance`. `CHECKLIST.md`, `CI.md`, `PRE_COMMIT.md`, `FORGEJO_ORGS.md`, `GIT_WORKFLOW.md` are the source of truth; this file documents only claude-run-specific deviations.
- Builder image: `dev.a8n.run/pandoras-box/rust-builder-musl:v1.0.0-rust1.94-alpine`. The binary still ships as a Generic Package for host installs. There is also a runtime image (CLAUDE-37): `oci-build/Dockerfile --target runtime` builds the daemon plus its pinned toolchain (`nu`, `claude`, `yt`, `fj`, `timeout`, `git`) on the builder image; CI publishes it to the Forgejo OCI registry as `dev.a8n.run/psa-systems/claude-run:{vX.Y.Z,latest}` with the same tag set as the binary, from its own workflow `.forgejo/workflows/build-image.yml` (split out of `build-binary.yml` in CLAUDE-94), and `compose.yml` runs the published image. The container user's `~/.claude/CLAUDE.md` is the slim bot file `deploy/bot-CLAUDE.md`, so the agent never inherits the operator's interactive global CLAUDE.md. See README "Containerized deployment".

- The web UI bootstraps itself: an exposed instance with no credential serves only `/setup`, which writes an argon2id admin hash to the `web_admin` table (`src/web_admin.rs`, migration `0020`) and is refused once one exists. `auth::resolve_gate` now returns a gate carrying whichever credentials exist (bearer token from `auth_token_ref`, DB administrator, or neither), and an unresolvable `auth_token_ref` is a `warn` with bearer auth disabled for the run rather than the old fail-closed that dropped the whole TCP listener. That old behaviour was unrecoverable in a container: the CLI that would store the secret is not the interface a container operator has. The gate holds the administrator behind an `Arc<RwLock<..>>` the setup handler swaps, so a first-run setup authenticates the next request with no restart. Sessions are HMAC'd with the admin's `session_key`, rotated on a password change, falling back to the token where no administrator exists. Where no administrator exists the pre-setup `auth_username` + token-plaintext login still works, so host installs are unchanged. The container image seeds `deploy/container-config.toml` (`bind = "0.0.0.0"`) into an empty config volume, because a loopback bind in a container is reachable from nothing outside it.

- Nothing runs without a Claude credential (`src/readiness.rs`). The scheduler tick, `Dispatcher::execute` and the trigger endpoint all consult `ReadinessGate` the way they consult `pause::PauseGate`, and the two states stay distinct: a pause is an operator decision, unready is an instance that was never finished. Ready means any of a `.credentials.json` in the agent config dir (on a host, the symlink to the operator's login), a stored API key, or `ANTHROPIC_API_KEY` in the env, so host installs are unaffected. The transition is logged once in each direction rather than per tick; the dashboard shows a banner and `/api/status` carries `ready` + `not_ready_reason`. This is what stopped a fresh container from querying YouTrack every tick and logging an auth error per action, on runs that could only have failed at the `claude` call and burned an attempt.

- `claude auth login` is brokered from the Settings Auth card (`src/claude_login.rs`), so the container gets a real subscription login and not just an API key. The CLI's redirect is a paste-the-code callback, not a `localhost` listener, and over pipes it prints the authorize URL then reads the code from stdin: the broker spawns it under the agent config dir, hands the URL to the page, and writes the pasted code back. The child is held in daemon state between the two requests because it owns the PKCE verifier; a refused code returns the CLI's own wording and keeps the session (the CLI re-arms its prompt), cancel and a 15-minute expiry kill it, and the spawn plus the bounded read run through `blocking::in_place` per CLAUDE-228.

- The daemon holds its own service logins, entered in the web UI (Settings -> Auth, the card at the top of `/settings`). `src/service_auth.rs` materializes them where the CLIs actually look: a single-file `yt` config at `<config_dir>/auth/youtrack.yml` named by `YOUTRACK_CLI_CONFIG` (exported once at serve start, before any child, so a later save needs no restart and a per-job `token_ref` still wins by setting the same var in the child's own env), a `keys.json` in the daemon's XDG data dir through the same `secrets::write_fj_keys` the per-job path uses, and an `ANTHROPIC_API_KEY` handed to `ClaudeInvoker` through an `Arc<RwLock<Option<String>>>` the Settings save swaps. The `config.auth` document (section `Auth`) stores only URLs, the Forgejo host, and the three fixed secret names; the tokens live encrypted in the secrets store. That store needs no pre-provisioned key and the runner owns it: `secrets::ensure_key` (serve start, and the CLI before it writes) puts it at `<config_dir>/secrets.key`, 0600. Config, not data, because the ciphertext is `state.db` in the data dir and a key beside its ciphertext defeats the point of encrypting the store; a key still at the old `<data_dir>/secrets.key` is MOVED on the next start. Generation happens only while the store is empty: a missing key with secrets already stored is a hard error naming them, never a silent replacement that would orphan them. `SecretsKey::load` is now a plain read with one behaviour. The key is extracted from wherever it sits on a line, so a SOPS-decrypted `data: AGE-SECRET-KEY-...` or an env-style file works as a key file, and a group- or world-readable key file loads with a `warn` rather than failing (an operator's delivery may be 0644 deliberately). This is what fixes the container's `no instance configured. Run 'yt auth login'` on every poll: the daemon's own provider calls had nothing but host auth, and a container has no host operator.

- Every `git` subprocess authenticates from the forge key store and reports why it failed (CLAUDE-252). `provider::shallow_clone` is the one clone path for all three actions, and `provider::git_error` builds every git failure as the exit code PLUS the tail of git's own stderr, redacted through `forge_log::redact` with the URL's userinfo passed as a known secret (the reason string reaches `run_events` and can reach a YouTrack comment, and the clone URL carries a token). Before it, `git clone exited 128` and `git push exited 1` were the entire diagnosis for a missing credential, an unknown host, a deleted branch, a rejected non-fast-forward and a protected branch alike. The `youtrack` action was also the only one cloning the UNauthenticated URL from the YouTrack VCS integration ("host git identity handles auth"), which is exactly what a container does not have, so every job failed at the pre step; it now resolves through `Forge::clone_url` like the other two, stripping the scheme from `repo_host` because that lookup wants a bare host, and falls back to the plain URL with a `warn` so a host install using a credential helper is unchanged. `{{clone_url}}` in the prompt stays unauthenticated: the agent must never be handed the token.

- The container's layout is flat (CLAUDE-253): `/config`, `/data`, `/state`, plus a tmpfs `/run/claude-run`, instead of seven XDG paths under `/home/claudebot`. The image sets `CLAUDE_RUN_{CONFIG,DATA,STATE,RUNTIME}_DIR` plus `XDG_CONFIG_HOME=/config` (yt), `XDG_DATA_HOME=/data` (fj, which has no config-dir variable and which `provider/cli.rs`, `update.rs` and `secrets.rs` resolve through `dirs::data_dir()`), `CLAUDE_CONFIG_DIR=/config/claude-agent-home` and `GIT_CONFIG_GLOBAL=/config/git/config`, so each tool store is a subdirectory rather than a mount of its own and compose is three volumes rather than seven. `CLAUDE_CONFIG_DIR` names the SAME dir `agent_home` seeds, so an `exec`-run `claude auth login` lands where the agent reads rather than in a second config dir that authenticates nothing. `$HOME` is scratch. A HOST install sets none of these and still resolves through XDG, which the `config.rs` tests cover. One migration wrinkle: `job_outcomes.stream_log_path` is absolute, so rows written under the old layout point at paths that no longer exist; the log search resolves a missing recorded path against the current logs dir (the stream page already recomputed), so a moved deployment does not silently search nothing.

- The container carries its own identity (CLAUDE-247). It bind-mounts NOTHING from the host: the operator runs `claude auth login`, `yt auth login`, `fj auth add-key` and `git config --global` INSIDE the container, one named volume per store (`claude-bot-{claude,youtrack-cli,forgejo-cli,git}` beside `claude-bot-{config,data,state}`), so the runner's credentials are separate from the operator's and the stack deploys where neither `$HOME` nor the invocation directory is reachable. Three pieces make that work. `src/agent_home.rs` treats a missing host login as a `warn` instead of aborting serve start (the old hard error crash-looped the container the operator needed to log into) and never removes a regular `.credentials.json`, because in the container that file IS the login rather than a link to the host's; the same guard covers `claude_config_dir` pointing at `$HOME/.claude`, where source and link are one path. `oci-build/entrypoint.sh` starts as root, chowns the mounted volumes (skipping `workdirs`, a tree of job clones the runtime user made) and drops to `claudebot` with `su-exec`, which is pattern 3 of `governance/CONTAINER_UID_GID.md` and a recorded exception to BUILD.md's non-root-start mandate; `user:` must therefore never be set in compose, and `docker compose exec` needs `--user claudebot`. `yt` and `fj` are prebuilt static binaries pulled from this org's Forgejo generic packages (`pandoras-box/{youtrack-cli,forgejo-cli}`) and checksum-verified, replacing a PyPI `youtrack-cli` that was a DIFFERENT project from the org's `yt` and a `cargo install forgejo-cli` that recompiled the crate every build.
- The governance template's `.env.example`, HOST_IP/PORT split, and fixed per-service port assignments do NOT apply. The daemon binds a unix socket by default (not in the container image, which runs `serve --no-socket`); the TCP web UI is reachable on `127.0.0.1:7321` by default (`WebConfig`, `src/config.rs`). The container runtime ships its own `compose.yml` (CLAUDE-37; see the builder-image note above).
- Action schema is documented in `actions/SCHEMA.md`. Authoritative; changes here ripple to both the runner and the doc.
- Not every action works code. `closed-issue-summary.yml` (`kind: closed-issue-summary`, `src/native/closed_issue_summary.rs`, CLAUDE-218) is the runner used as a REPORTING tool: it counts and lists the issues closed in a rolling window across a project list, files that report as a new issue, and links it to a nominated parent as a subtask. It clones no repository, starts no agent session, and opens no pull request. It is partitioned off `youtrack.yml` on the `AI Agent` axis (the worker pins `Queued`; a reporting `query` must pin its own value), the same "one action, one job" split CLAUDE-215 made for audits on the project axis. `shipped_action_queries_are_disjoint` in `src/action.rs` guards the partition; `youtrack.yml` deliberately writes no negation, because YouTrack 400s a query naming an `AI Agent` value that is not in the bundle.
- The state store is SQLite or PostgreSQL, chosen by the operator (CLAUDE-250). `src/db.rs` opens ONE `sqlx::AnyPool` (`db::DbPool`) for either, so no module outside it names a backend type, and it holds the two migration sets: `migrations/sqlite/` is the original twenty files, byte-identical so a deployed `state.db` matches its recorded checksums and re-runs nothing, and `migrations/postgres/0001_init.sql` is a hand-written squash of their end state (`BIGINT` for every integer, `DOUBLE PRECISION` for `REAL`, `BYTEA` for `BLOB`, `GENERATED BY DEFAULT AS IDENTITY` for the autoincrement keys, boolean-ish columns left as integer 0/1). `Any` forwards SQL unchanged, so `db::q` is the chokepoint every statement passes through: it renumbers `?` / `?N` into `$n` for Postgres and expands the two dialect-neutral functions the call sites are written in, `strpos(haystack, needle)` and `elapsed_seconds(from, to)`. Everything else is spelled portably in place (`COALESCE`, `ON CONFLICT DO NOTHING`, `CAST(... AS BIGINT)` around a `SUM()` over an integer, `<table>.<col>` on the right of a `DO UPDATE SET`, no negative `LIMIT`), and integer 0/1 columns decode through `db::flag` because `Any` will not coerce an integer to a `bool`. Selection is a bootstrap key, not a DB-backed setting: `[database] url`, overridden by `CLAUDE_RUN_DATABASE_URL`, overridden by the contents of the file named by `CLAUDE_RUN_DATABASE_URL_FILE`. Unset is SQLite; an unknown scheme or an unreachable server stops the daemon rather than falling back. `compose.yml` carries `claude-bot-postgres` behind a `postgres` profile. Setting `CLAUDE_RUN_TEST_DATABASE_URL` re-runs the WHOLE test suite against Postgres (one schema per fixture pool), which is what CI does after the SQLite pass. See README "State store backend".
- Switching backends carries the data over with `claude-run import` (CLAUDE-251, `src/import.rs`). Selecting Postgres only opens an empty instance, and the data that would be lost is not disposable: `secrets` holds the ciphertext for the web token, the webhook HMACs and the service logins, `web_admin` the argon2id hash and the session key, and `attempt_counters` / `daily_ledger` are what stop a job being retried past its cap. The copy is schema-driven, not typed per column: the source's own `pragma_table_info` gives the column list and the declared type that decides the Rust type each value round-trips as (SQLite affinity is what makes that sound), so a migration that adds a column needs no edit here. The target is whatever `config::resolve_database` resolved, never a flag of its own, so the import and the daemon cannot disagree about where the rows went. `import::TABLES` is the hand-maintained foreign-key order and is compared against the live catalog on every import (and by `the_table_list_matches_the_schema`), so a new table fails the copy instead of being silently left behind; `IDENTITY_COLUMNS` is the four Postgres sequences advanced past the copied ids, without which the daemon's first insert collides with imported history. The source is opened `mode=ro` and never written, the whole copy is one transaction, a target holding rows is refused unless `--allow-nonempty`, and per-table source/copied/target counts are printed and checked before the commit rather than a bare success line. A source older than the build is refused naming every missing column, because a read-only open cannot apply the pending SQLite migrations.
- Config splits into bootstrap vs runtime settings (CLAUDE-101). `config.toml` holds only bootstrap keys the daemon needs before it can open the DB and bind: `[database] url` (CLAUDE-250), `[web]` and `[daemon]` binary overrides (`nu_binary`, `claude_binary`). Everything runtime-tunable is DB-backed (one JSON document per section in the `settings` table, keyed `config.<section>`) and edited on the web Settings page (`/settings`) or via `GET`/`PUT /api/settings/<section>`. The DB-backed sections are `config.mint`, `config.update`, `config.webhook`, `config.webhook_comment` (CLAUDE-220), `config.log_filter`, `config.workdir_gc`, `config.stream_log_gc` (CLAUDE-245), `config.preferences`, `config.concurrency`, `config.db_retention`, and `config.claude` (CLAUDE-239: the global default `--model`, which an action's own `claude.model` overrides; CLAUDE-259 added `effort` on the identical precedence, with the documented set `low | medium | high | xhigh | max` advisory only, so an unrecognized level is warned about once and then passed through rather than rejected or substituted). The first four of those (`[mint]` / `[update]` / `[webhook]` / `[daemon].log_filter`) were moved out of `config.toml` and carry the one-time import; the rest are DB-only from birth and have no import path. The serde structs in `src/config.rs` stay the schema; `src/settings.rs` owns the store, the live-apply (`LiveSettings`), and the one-time import then breaking-on-conflict migration (`migrate_config_file`, run at serve start). A moved section present in both `config.toml` and the DB refuses to start, naming it, and `[webhook_comment]` is rejected by the file parser outright (it is absent from `OnDiskConfig`).
- Global pause is one DB flag (`global_pause`, `src/state.rs`) honoured at EVERY entry point (CLAUDE-223): the scheduler tick, `Dispatcher::execute`, the daemonless `claude-run run`, the trigger endpoint (`409` naming the pause, not a lying "queued trigger" ack), both webhook listeners (accept-and-drop with `2xx`, via the shared `webhooks::paused_accept_and_drop`), and the per-job checkpoints of every runner. That last one is `src/pause.rs`: a TTL-cached `PauseGate` (daemon-wide, refreshed each scheduler tick, so the blocking automerge wait can read the last value with no `await`) plus a run-scoped `RunPause` that records whether the pause actually stopped work. A run it stopped finishes with `exit::PAUSED` (1), badged "paused" and distinct from an operator cancel (130); its unprocessed jobs consume no attempt. A failed gate read is logged at `error` and treated as NOT paused, so a transient DB error cannot silently stop the daemon. The operator surface is the Activity card on `/about` (Pause / Resume plus a 2s-polled busy / idle / unknown indicator, `templates/activity.html` + `GET /about/activity`); `unknown` is a distinct state precisely so a failed activity query never reads as "safe to restart". The same snapshot is on `/api/status` as the `activity` block. See README "Global pause and the restart-safety workflow".
- No blocking work runs on a tokio worker thread (CLAUDE-228). `src/blocking.rs` `in_place` wraps every synchronous subprocess and sleep reached from an async context: the `yt` / `fj` / `git` exec in `provider::cli::ProcessRunner`, `ClaudeInvoker::invoke`'s spawn-and-wait, the `nu` exec in `src/snippet.rs`, and each runner's sync `run_pre` / `finalize` / gather / cleanup call. It is `block_in_place` behind a `RuntimeFlavor::MultiThread` check (that call panics on the `current_thread` runtime `#[tokio::test]` builds), chosen over `spawn_blocking` because it takes a bare `FnOnce` and the call sites keep their borrows. Left inline, one 3600s `claude` session pinned one worker for its whole duration, tasks holding sqlx pool connections went unpolled, and the daemon logged `pool timed out while waiting for an open connection` while no single statement was slow. Two supporting pieces landed with it: `concurrency::GatherGate`, a per-action marker so the scheduler skips a pickup whose previous gather is still running (overlapping RUNS stay deliberate per CLAUDE-162; overlapping GATHERS were never intended), and `state::RunGuard`, which closes a `run_begin` row on every exit path including an early `?`, so a transient error can no longer strand a row that the web UI renders as a running job. The DB-level sweeps are the backstop a long-lived daemon never reaches: `state::reap_orphaned_runs` at serve start closes every row still open as `exit::UNEXPECTED` (nothing cancelled it; the count logs at `warn`), and `state::cancel_orphaned_runs` at shutdown closes what the stop actually cancelled as `exit::CANCELLED`. `state.rs` also carries the mechanical pairing test that fails if a runner ever calls `run_begin` without a `RunGuard`. `src/db.rs` states the pool's `max_connections` (16), `acquire_timeout` (30s) and `acquire_slow_threshold` (5s) explicitly rather than inheriting sqlx's defaults.
- Every YouTrack write the runner makes goes through one run-scoped wrapper (CLAUDE-234): `provider::AuditedTracker`, built per run from `provider::IssueWriteAudit` and wrapped around whichever `IssueTracker` the run resolved. It does two things the prompt cannot be trusted to do: it spends one slot of `limits.max_issues_per_run` (default 25, `provider::DEFAULT_MAX_ISSUES_PER_RUN`) per `create_issue` and refuses past the ceiling BEFORE `yt issue create` is invoked, and it journals one `youtrack issue write` line per create and per update carrying the run id and the issue key. A refusal is a typed `Error::IssueCapReached`, a `warn`, and a `run_events` row on the run, so a truncated filing run never reads as clean. The ledger is per RUN, not per backend: the youtrack action builds a backend per job and the webhook mint backend is daemon-lifetime, so a counter held on the backend would be wrong in both directions. Deletes stay denied by omission (the trait exposes none) and `no_delete_on_the_tracker_surface` fails if one reappears. The cap covers the runner's own provider calls, not the `yt` calls an agent session makes inside its workdir.

- The stream-log relay reports its own I/O failures instead of truncating in silence (CLAUDE-233). `relay_stamped_stdout` (`src/claude.rs`) is the only writer of `logs/<action>/streams/<key>-attempt-<n>.jsonl`, and it used to `break` on a write error with the error discarded. When the log partition filled, it stopped mid-line, claude kept running and exited 0, `parse_final_result` found no `result`, and the run was failed non-transiently as "claude stream did not end with a result event" - blaming the agent for a silence the runner produced, and burning an attempt against `max_attempts_per_key`. The relay now returns `io::Result`, `invoke` carries the reason out of the wait block, and a relay that died before the terminal `result` yields a `transient` failure naming the write error and the log path (`relay_failure_result`), so no attempt is spent; when the `result` was already captured the run still finalizes from it and the truncation logs at `warn`. The forensic signature of the old bug in an existing log is a file ending mid-line at an exact multiple of 4096, the page boundary where the kernel's short write stopped.

- `logs/` is bounded by its own sweep (CLAUDE-245). Nothing deleted stream logs before it: `crate::gc::sweep` walks `workdirs/*/*` and `crate::retention::sweep` prunes DB tables, and neither looked at `logs/`, so the directory only ever grew (2473 files / 2.8 GB on host-a, oldest five months back). That is the root cause of CLAUDE-233 rather than a separate bug: the full log partition is what made the relay's write fail. `crate::gc::sweep_stream_logs` is the second sweep in the same module, deleting `logs/<action>/streams/*.jsonl` past `config.stream_log_gc.retention_days` (default 30) and logging its deleted / kept / bytes-reclaimed tally every pass at `info`. `daemon::stream_log_gc_loop` schedules it beside the other two on the `GC_TICK_SECS` cadence, first tick at serve start, reading the live handle so a Settings save applies next pass. What keeps an in-flight run's log is `daemon::inflight_stream_log_jobs`: the `(action, job_key)` pairs from `run_inflight_jobs` joined to runs with `ended_at IS NULL`, kept regardless of age, because a long `claude_timeout_seconds` job can outlive any window while its log is still being written. A failed read of that set skips the pass rather than sweeping with an empty set, since the wrong guess deletes a live run's only transcript.

- Two inbound webhook listeners, deliberately separate because their credentials differ in kind: `POST /webhooks/forgejo/<source>` (`src/web/webhooks.rs`, CI-failure triage, read-only `log_token_ref`) and `POST /webhooks/forgejo-comment/<source>` (`src/web/comment_webhooks.rs`, `/claude` comment commands, write-scoped `write_token_ref`). The comment listener has TWO routes on one action, chosen by whether the thread is a pull request: a PR comment clones the head branch and pushes (CLAUDE-220), a plain-issue comment mints a `AI Agent = Queued` YouTrack issue for the `youtrack` action to work (CLAUDE-221) and clones nothing. The gate / trigger parsing / bot-login drop / dedupe key / caps are one implementation shared by both routes. They SHARE the signature verifier, the single replay-store instance, the rate-limiter type plus its builder, the repo allow-list matcher, and the run-accounting opener. Each surfaces as its own synthetic action (`webhook-forgejo`, `webhook-forgejo-comment`) with its own Pause switch; both reserved names come from `crate::web::SYNTHETIC_ACTIONS`, the one predicate the daemon scan guard, the API, and the web layer all read.

## Phases

The Rust port is complete: all six phases below are merged. This table is the historical record of that rollout, kept because code comments across the tree still cite these phase numbers.

| Phase | Scope                                                                | Status                          |
|-------|----------------------------------------------------------------------|---------------------------------|
| 1     | `run` / `migrate`, all core modules, SQLite-backed state             | merged                          |
| 2     | `serve [--detach]`, scheduler, unix-socket API, lock, pause-in-DB    | merged                          |
| 3     | Web UI (axum templates + HTMX + SSE), TCP listener, log streaming    | merged                          |
| 4     | Action edit / import / export through the API                        | merged (CLAUDE-7)               |
| 5     | Token auth for non-loopback binds                                    | merged (CLAUDE-48)              |
| 6     | Retention policy enforcement on the unbounded history tables, polish | merged (CLAUDE-172, CLAUDE-175) |

Two unrelated numbering schemes both say "Phase N", and a bare `grep 'Phase 3'` returns hits from both. The roadmap phases in this table are one (e.g. `src/web/mod.rs` "Phase 3" = Web UI, `src/auth.rs` "Phase 5" = token auth). The separate native-actions epic (CLAUDE-30..CLAUDE-34, tracked under CLAUDE-25) is the other; its comments carry the "native-action" qualifier (e.g. `src/native/youtrack.rs` "Phase 3 of the native-action epic" = CLAUDE-32, which is NOT roadmap Phase 3). Tell them apart by that qualifier and the CLAUDE-30..34 / CLAUDE-25 issue range; a bare "Phase N" with no "native-action" wording refers to this table.

Cross-cutting (not a numbered phase): a container runtime (CLAUDE-37, made self-contained in CLAUDE-247) runs the daemon and its spawned `claude` children in an isolated `$HOME` with a slim bot CLAUDE.md and its own logins, decoupled from the host's operator config. See `oci-build/Dockerfile` (`runtime` target), `oci-build/entrypoint.sh`, `compose.yml`, and `deploy/bot-CLAUDE.md`.

## Working on this repo

- Branch off `main` per `governance/GIT_WORKFLOW.md`. Run `just pre-commit` (or rely on the installed hook) before pushing.
- `just check` runs the same fmt + clippy + build + tests CI runs.
- The task runner is the shared `psa-systems/common` recipe set, vendored as the `common` submodule (`git submodule update --init` after a fresh clone). `justfile` configures it through variables (`pre_commit_mode := "docker"` + `dev_image` because there is no `compose.dev.yml`, `test_args := ""` so the library-target unit tests are not skipped) and overrides only `default`, `check`, and `run`. Prefer setting a common variable over shadowing a shared recipe. `default` is redefined locally (as the file's first recipe) because just resolves the default recipe by source order and a top-level definition outranks the imported one, so without it a bare `just` runs whichever local recipe comes first instead of common's `just --list` (CLAUDE-201). CI keeps its own `.forgejo/workflows/check.yml` rather than calling common's reusable one, which hardcodes `cargo test --bins`; making that configurable is tracked in #PC-6.
- Daemon smoke-test pattern: `CLAUDE_RUN_*_DIR=/tmp/...` env vars + a stub `claude` on `PATH` (see `src/bin/claude-run.rs` smoke tests for the shape).
- The legacy `scripts/claude-run.nu` is gone as of the governance-conformance PR. The Rust binary is the only runner.
